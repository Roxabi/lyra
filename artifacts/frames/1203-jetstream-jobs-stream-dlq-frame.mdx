## Problem

The job dispatch bus has contracts (#1045 `JobEnvelope`/`JobResult`/`JobProgress`, #1619 `WorkEnvelope`+`job_id`, #1793 unified taxonomy) but no durable substrate. Without a JetStream stream binding the dispatch subjects, every future worker (#1046 onward) subscribes plain core NATS — no replay, no ack tracking, no DLQ, no backpressure. A worker restart loses every in-flight and queued job silently.

This is the last open blocker of both epics: #1044 (worker fleet — chain #1046→#1053 all depend on it) and #1792 (Shape D — dispatch-side work targets the same substrate). Everything queued behind it is unblocked the day it lands.

**Drift since issue creation (2026-05-14, 55 commits on cited paths):** the issue body predates the ratified taxonomy and binds the stream to `factory.job.>`. Per the post-#1793 SSoT (`docs/architecture/job-model.md` §Transport tiers), that hierarchy now carries the **per-job pub/sub facets** (`factory.job.<job_id>.result/.progress/.steer/.opened/.closed`), which are explicitly **at-most-once core NATS** — the SSoT states "Do NOT promote `factory.job.<id>.result` to JetStream — notification ≠ data." The at-least-once JetStream tier covers `turns.write` and the **dispatch queue `factory.jobs.<job_name>`** only. The stream definition, consumer filters, and DLQ subjects in the issue body must all be re-anchored onto the `factory.jobs.*` dispatch family at spec time (the issue's own 2026-06-11 backlog-sweep note demands exactly this revalidation).

## Who

- **Primary:** worker-fleet implementers (#1046 `factory-code-worker` Quadlet, #1047 bootstrap + JobHandler registry) — need a known durable substrate to bind durable consumers against.
- **Secondary:** hub (dispatch-side publisher — ACL grant missing today, see Constraints), `monitor` identity (DLQ subscriber — grant missing today), ops on M₁ (stream visibility via `/jsz`, replay/backup via hub seed + nats CLI), existing omp dispatch lane (#1812 — see Constraints).

## Constraints

- **Taxonomy (ratified, #1793/#1794):** dispatch = `factory.jobs.<job_name>` (`<domain>.<verb>`, e.g. `factory.jobs.vault.add`); per-id facets = `factory.job.<job_id>.<facet>` (core pub/sub, NOT this stream). Consumer filters in the issue body (`factory.job.vault.>`) are stale → `factory.jobs.vault.>` etc. The issue body's DLQ subjects `factory.job.dlq.<domain>` are also stale (singular family) — epic #1044 reserves **`factory.jobs.dlq.<domain>`** (plural); spec must use the plural form.
- **Existing dispatch traffic (discovered at frame):** `factory.jobs.omp` is already live as a **core-NATS** queue-group lane — `omp-worker` identity subscribes it (`src/factory/adapters/omp/omp_worker.py`, queue group `omp-workers`, #1812); hub-side publish wiring arrives with #1813. A WorkQueue stream binding `factory.jobs.>` would capture omp dispatch messages with no bound consumer → unconsumed accumulation to stream limits. Spec must decide: explicit subject enumeration (exclude `factory.jobs.omp`), wildcard + omp consumer migration, or wildcard + documented accumulation bound.
- **DLQ routing is not automatic** in JetStream WorkQueue streams — max-deliver exhaustion does not republish anywhere by itself. Mechanism is a spec decision (advisory-consumer vs explicit republish), and each option carries its own ACL grant: advisory → `monitor` subscribe on the JS advisory subjects for the stream; republish → the republishing identity needs publish on `factory.jobs.dlq.>`. Spec must enumerate the grants for the chosen mechanism before ACL regen.
- **ACL grants required (verified absent in `deploy/nats/acl-matrix.json`):** (1) hub publish `factory.jobs.>` — hub's publish list today carries only `factory.job.*.steer` from the jobs family; (2) `monitor` subscribe `factory.jobs.dlq.>` — monitor identity holds only `factory.monitor.>` pub+sub. Plus the per-mechanism DLQ grant above. Any `acl-matrix.json` edit triggers the full fan-out (project memory): regen 4 generated artifacts AND hand-mirror the exact diff into `tests/scripts/fixtures/v3-pre-grant-group.json`; the equivalence checks are CI-only — clean local pre-push ≠ green CI.
- **Stream naming convention (existing fleet):** `FACTORY_TURNS` (WorkQueue, `factory.turns.>` — provisioned by the turn-writer process, useful as the WorkQueue+durable-consumer shape reference), `FACTORY_AUDIT` (LIMITS), `FACTORY_OUTBOUND_AUDIO`. Bare `JOBS` from the issue body breaks convention; final name fixed at spec.
- **Bootstrap pattern (decided in issue, still valid — precedents corrected at frame):** hub-provisioned at boot, idempotent ensure (add→BadRequestError→update). The paved precedent is the **ADR-079 sole-provisioner pattern** (#1525): hub provisions stream `FACTORY_OUTBOUND_AUDIO` + KV bucket before `announce_hub_ready()`; satellites are bind-only. `factory-state` KV provisioning (`bootstrap/wiring/kv_watch_channels.py`) follows the same shape. Hub already holds `$JS.API.>`. Cold-boot ordering: provision before `announce_hub_ready()` so workers' lazy consumer-bind never races a missing stream.
- **Module placement governance:** any **new subdirectory** under `src/factory/infrastructure/` requires its own ADR (`src/factory/infrastructure/CLAUDE.md` governance rule). Spec must either assign an ADR for `infrastructure/jobs/`, co-locate in an existing subdir with justification, or place the ensure-stream helper in `packages/roxabi-nats` (sidesteps the rule; evaluate explicitly).
- **Quality gates that will fire on this PR:** `secrets_drift` (deploy/ changes — unit Secret= ⊆ quadlet.toml required_secrets), `doc_drift` (new `factory.jobs.>` subjects referenced in docs must exist in src or stay un-backticked), `architecture_snapshot` (CURRENT.generated.md regen, pre-push/CI-only), `import_layers` (.importlinter on new bootstrap imports), `str_exc_bus_bound` (no `str(exc)`/f-string-exc into NATS-published fields in DLQ handling — ADR-073).
- **Smoke tests:** follow the mock-based AsyncMock pattern of `tests/infrastructure/turn_writer/test_stream_setup.py` (no live-NATS fixture): (a) ensure add-success path, (b) BadRequestError→update path; DLQ-path coverage per chosen mechanism.
- **WorkQueue retention semantics:** non-overlapping consumer filters required; day-1 consumers: `code-worker` (deferred to #1046/#1047 — consumer creation is lazy) + DLQ path per chosen mechanism.
- **R1 day-1** (single NATS server on M₁); R3 only if/when M₂ joins a cluster.

- v2 observability stream over `factory.job.>` (LIMITS retention, dashboard replay) — #1800's scope, a **different stream** with different retention; do not conflate with this WorkQueue dispatch stream.
- #1795 (JobResult → pub/sub + 3-tier codification) and #1798 (sub-jobs on `factory.job.<id>.*`) — both live on the core pub/sub tier (`factory.job.*`), no subject overlap with this stream expected; cross-ref at spec time.
- Per-job-id facet ACLs (`factory.job.*.*` grants) — #1812 pattern, extended per-worker as workers land.
- Active-jobs registry KV (#1796) — parallel work, KV tier.
- Folding `request_id` into `job_id` (#1621), `job_id` hard-require flip (#1841).

## Premise Validity

**Success in 6 months:** a WorkQueue JetStream stream over the `factory.jobs.*` dispatch family (final name per spec) exists on M₁, provisioned idempotently at hub boot from a repo-versioned definition; #1046/#1047 workers bind durable consumers against it; a worker restart mid-job loses zero queued jobs (replay observed); deliberately failed jobs surface on `factory.jobs.dlq.<domain>` and the `monitor` identity sees them. Smoke tests for both paths exist and pass.

**Failure in 6 months:** By 2026-12, either (a) `/jsz` on M₁ reports the stream with **0 durable consumers** on its dispatch filters while job workers are running (workers bypassing JetStream on plain core NATS), or (b) the stream's binding captured per-id pub/sub facets or the live omp lane (unconsumed messages accumulating to stream limits / observability subjects swallowed by WorkQueue single-delivery). Either condition = this slice added config, not durability → rebind/redesign.

**Simplest alternative:** extend `deploy/nats/bootstrap_streams.py` (the deploy-time provisioning script that already creates `factory-events`/`factory-metrics` with the same idempotent add→BadRequestError→update pattern, repo-versioned and converge-integrated).
**Why not simplest:** deploy-time provisioning runs only on deploy events; the stream must exist on **every** boot path — fresh machine, container restart after NATS data loss, M₂ joining later — and before the hub's first dispatch publish. Hub-boot ensure (ADR-079 sole-provisioner) is the converge point that exists on every restart and already orders provisioning before `announce_hub_ready()`. The two are not exclusive — spec may keep `bootstrap_streams.py` as an ops-side convergence mirror — but the authoritative ensure belongs to the hub boot path, matching `FACTORY_OUTBOUND_AUDIO` and `factory-state`.
