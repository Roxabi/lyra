## Source

Issue #1018: Ruff BLE001 flags 121 blind `except Exception:` catches across 67 files. Fix strategy
defined in issue (4 categories). This analysis validates and corrects the estimates, identifies
specific replacement exception types per category, and surfaces implementation risks.

## Problem

121 blind `except Exception:` catches obstruct enabling BLE001 as a quality gate. The catches fall
into 4 structurally different patterns — a single mechanical pass cannot fix them all correctly.
The issue's count estimates are off: category B is ~47 violations (2× the estimate), category C is
~38 (3× the estimate). Both require careful per-violation review before implementation.

## Outcome

`uv run ruff check --select BLE001 .` → 0 violations, no file-level blanket noqa, and BLE001 added
to the default `[tool.ruff.lint] select` list in `pyproject.toml`.

## Appetite

1-week cycle — mechanical fix with categorization overhead. Parallelizable by domain area.

## Shapes

### Shape 1: Batch-by-category (recommended)

Enumerate all violations by category first (analysis artifact as authoritative map), then fix
each category in a single sweep. Each fix pass is uniform within a category.

**Execution order:** A → B → C → D (ascending risk; A fails at test-time, D is tests).

**Trade-offs:**
- Pro: Faster per-file — same decision applied to all violations of a type; less context switching
- Pro: Reviewable in category-scoped commits
- Con: Requires up-front categorization (done in this analysis)
- Con: C-category requires individual logging audit per violation

**Rough scope:** M — ~120 single-line changes across 67 files + 1 pyproject.toml update

### Shape 2: File-by-file

Process each of the 67 files sequentially, applying contextual judgment per violation.

**Trade-offs:**
- Pro: No pre-categorization pass needed
- Con: Slower — context-switch overhead per file
- Con: Risk of inconsistent decisions across similar patterns in different files
- Con: Cannot parallelize across agents easily

**Rough scope:** M — same number of changes, higher coordination cost

## Fit Check

**Shape 1 wins.** The categorization is already complete in this analysis. Batch-by-category
allows parallelizing the fix across 2–3 agents (e.g., packages vs src/adapters vs src/core) with
no overlap risk if files are partitioned by domain.

fall back to `# noqa: BLE001  # <transport> teardown/op: any transport error is safe to swallow`

Pattern: top-level pool/middleware/bootstrap boundaries. These intentionally catch broadly because
they sit above unknown caller code. Fix: verify each has `log.exception(…)` or `exc_info=True`
**before** adding noqa; add the missing log line if absent.

- `session_lifecycle.py:146,182` — `log.warning(…, exc_info=True)` ✓

## Implementation Risks

| Risk | Severity | Mitigation |
|------|----------|-----------|
| `nats.errors.Error` may not cover all NATS transport errors | Medium | Verify against `nats-py` error hierarchy; `nats.errors.Error` is the base for all NATS errors |
| Discord exception hierarchy: `HTTPException` vs `DiscordException` | Low | `discord.HTTPException` is narrower; use `discord.DiscordException` at boundaries |
| Category C silent violations — adding noqa without logging audit first | High | **Mandatory audit**: grep for `except Exception` + no `log.exception` / no `exc_info=True` in body before adding noqa |
| `_serialize.py:130` — `get_type_hints` raises `NameError`/`AttributeError` for forward refs in user-defined types; cannot narrow | Medium | noqa is correct; comment must explain |
| Tests `test_pool_manager.py` — the broad catch IS the test subject | Low | noqa + comment; do not narrow or tests break |
| `pyproject.toml` BLE001 enable must be the final commit | Medium | Add as last step; if any violation remains, ruff will catch it in CI |
