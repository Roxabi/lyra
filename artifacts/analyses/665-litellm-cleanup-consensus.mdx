## Problem

PR #1196 (`chore(llm): drop dangling "litellm" backend value`) ships a tight cleanup of the
abandoned in-process `LiteLLMDriver` plan. `/code-review` surfaced 8 findings on the result.
The user clarified mid-review that **Ollama is not a planned in-process Lyra backend either** —
it has been removed and hidden behind the `llmCLI` worker over NATS, alongside LiteLLM and any
other multi-provider integration. The canonical path for everything non-Claude is:

```
lyra hub → backend = "nats" → NATS → llmCLI worker → LiteLLM lib → [Ollama, llama.cpp, …]
```

That reshapes findings #2 (add `"nats"` to `_VALID_BACKENDS`) and #3 (`"ollama"` is dangling
just like `"litellm"` was) from out-of-scope nitpicks into the coherent completion of what
this PR started. The panel was asked to settle the scope of THIS PR — concrete patches,
ordered for `/fix`.

| α | Focus |

## Consensus ρ

The PR must reach `_VALID_BACKENDS = {"claude-cli", "nats"}` — drop `"ollama"`, add `"nats"` —
and the `agent_factory._create_agent` dispatch branch at line 144 drops `"ollama"` in the same
commit. Add a negative `test_backend_litellm_rejected` (and a symmetric `test_backend_ollama_rejected`
+ positive `test_backend_nats_accepted`) against `_validate_backend_model`. Restore the
`(future / unused)` annotation on the `base_url` / `api_key` docstrings — the fields are dead
weight in code but kept for forward-compat, and the unqualified docstring misleads. Append a
one-clause NATS auth caveat to `docs/QUICKSTART.md:161`. Append a dual-hint to the
`_validate_backend_model` error message so ex-`"litellm"` users get guidance toward both
`"claude-cli"` (subscription, zero setup) and `"nats"` (multi-provider, needs NATS auth).
Update `docs/agent-management.md:59` Validation Rules to match the new set. Update the
`ModelConfig` docstring (lines 37-38) to reflect `{"claude-cli", "nats"}`. Defer
`ModelConfig.backend` `@field_validator` (#4), the `llm/CLAUDE.md:35` table redesign (#5),
and the eventual removal of the dead `base_url`/`api_key` fields — all separate concerns.

### Rationale

`_VALID_BACKENDS` is a **closed dispatch contract**, not a "future plans" enum. The PR was
filed to fix exactly the failure mode that occurs when the set diverges from real dispatch:
a value passes validation, then either crashes (`"litellm"` → `KeyError`) or silently routes
wrong (`"ollama"` → quietly serves claude-cli). Removing one dangling value while leaving an
identical one is half-coherent — the next person reading `_VALID_BACKENDS` after merge would
have to repeat the same investigation we just did. The architect made this the blocking
concern: `{"claude-cli", "ollama"}` is unshippable; `{"claude-cli", "nats"}` is the truthful
set.

The security panelist's blocking concern (NATS auth caveat in QUICKSTART) is a 5-word fix and
materially changes user behavior: today's QUICKSTART text actively recommends `backend = "nats"`
without mentioning that an unauthenticated NATS server bypasses Lyra's `GuardChain` at the
worker boundary. Cheap to fix, expensive to skip.

DB audit (per backend-dev): zero rows with `backend = "ollama"` in production. No migration
shim needed — removing `"ollama"` from `_VALID_BACKENDS` breaks nothing in the field.

### Trade-offs

- **Scope expansion vs. coherence.** Original PR was 4 files / 7+ lines. Consensus expands to
  ~6 files / ~30 lines. Still tight, still single-purpose ("close the dangling-backend drift,
  completely"). Shipping the half-coherent first commit + a `#1197` follow-up to finish
  trades 5 minutes of work for cognitive load on every future reader.
- **`_VALID_BACKENDS` ↔ `agent_factory._create_agent:144` must stay in sync.** Two SSoT layers
  for the same closed set is a maintenance hazard, but consolidating (factory derives from
  the constant) is a bigger refactor than this PR is for. Leaving the duplication is the
  pragmatic call; the negative test catches regressions.
- **Closed enum vs. forward compatibility.** `"ollama"` being out of the set means a future
  in-process `OllamaDriver` (if it ever lands) will need an explicit `_VALID_BACKENDS` update
  in its own PR. That is the desired property — additions should be deliberate, not vestigial.

## Alternatives

| ω | Proposed by | Rejected because |
|---|---|---|
| Keep `"ollama"` as forward reservation in `_VALID_BACKENDS` | (anti-option) | Reservation slots without dispatch paths *are* the bug this PR is closing — `"litellm"` was exactly that. |
| Make `_VALID_BACKENDS` an open guard rail (warn but accept) | (anti-option) | Defeats the purpose of `lyra agent validate` as a pre-runtime correctness gate. |
| Auto-translate `backend = "ollama" → "nats"` at load time with deprecation warning | backend-dev considered, rejected | DB audit shows 0 production rows with `"ollama"`. Migration shim is dead weight + a confusing code path. |
| Add `@field_validator("backend")` on `ModelConfig` (#4) | backend-dev recommended | Single-panelist support; negative test is naturally writable against `_validate_backend_model` directly; adds a second validation layer for a single closed-set check. Defer to a follow-up if a broader validation consolidation lands. |
| Remove `base_url` + `api_key` fields entirely (true dead code) | security-auditor considered | DB schema migration risk (rows may persist values); breaks the established `exclude={"api_key"}` pattern at `cli_nats.py:257`; out of scope for a backend-enum cleanup. Track as separate cleanup. |
| Suggest `"claude-cli"` only in migration error | security-auditor | Misses the multi-provider intent of ex-`litellm` users; backend-dev pushed back. Compromise: list both. |
| Suggest `"nats"` only in migration error | backend-dev | Pushes users toward a backend that requires auth infrastructure they may not have. Compromise: list both, `"claude-cli"` first. |
| Defer NATS auth caveat to a docs follow-up | architect | Security panelist's blocking concern; one clause is sufficient; trivial to include now. |

## Dissent

None on direction. Two 2-1 splits resolved by compromise:

1. **Migration error wording** — security wanted `"claude-cli"` as the primary suggestion
   (no-setup default); backend wanted `"nats"` (multi-provider replacement). Resolved by
   listing both, with `"claude-cli"` first (no infrastructure prerequisite).
2. **QUICKSTART NATS auth caveat** — security raised as blocking, architect classified
   as cosmetic / out of scope. Resolved in security's favor: the clause is one sentence and
   the change is in a user-facing recommendation that materially shifts security posture.
