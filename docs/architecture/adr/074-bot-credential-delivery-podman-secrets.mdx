## Status

Accepted — 2026-05-24

## Context

Post-#417 Lyra scales to multiple bots per platform (Telegram + Discord), each independently
provisioned and rotatable by the operator on M₁ (`lyra-hub` role).

The pre-#1057 credential model consisted of three interlocked layers:

- **`bot_secrets` SQLite table** in `~/.lyra/config.db` — rows of `(platform, bot_id, token,
  webhook_secret)`, Fernet-encrypted at rest.
- **`LyraKeyring`** — loads or creates `~/.lyra/keyring.key`; provides the Fernet key.
- **`CredentialStore.get_full()`** — decrypts and returns bot credentials at adapter bootstrap.

This layer was deleted in #1057 (Phase 3 of Epic #1049, shared-state migration). The rationale:

- The DB-at-rest encryption requires a master key (`keyring.key`); the key is itself a secret
  that must be delivered to every adapter container, widening the attack surface.
- Per-bot rotation required a DB write + adapter restart — no native per-secret granularity.
- Config.db was already mounted read-only in adapter containers; the credential path was the
  last non-read-only consumer.
- Podman secrets are already the delivery mechanism for NATS nkeys and NATS auth tokens in the
  Lyra Quadlet ecosystem (ADR-055). Extending the same pattern to bot tokens avoids a second
  credential plane.

Issue #1057 replaces the credential layer with Podman secrets mounted into each adapter
container at bootstrap. The spec (`artifacts/specs/1057-bot-token-podman-secrets-spec.mdx`)
defines the full data model, CLI affordances, migration command, and success criteria.

## Options Considered

### Option A: Podman secrets (chosen)

Two secrets per bot, mounted via `type=mount` into the adapter container:

```
Secret=lyra-bot-<platform>-<bot_id>,type=mount,target=bot_token-<bot_id>,mode=0400,uid=1500,gid=1500
Secret=lyra-bot-<platform>-<bot_id>-webhook,type=mount,target=bot_webhook-<bot_id>,mode=0400,uid=1500,gid=1500
```

Files land at `/run/secrets/bot_token-<bot_id>` and `/run/secrets/bot_webhook-<bot_id>` inside
the container. Rotation: `podman secret create --replace` + `make <svc> restart`. CLI surface:
`lyra bot secret install / rm / list / migrate`.

- **Pros:** native to the Quadlet + Podman stack; per-bot granularity at install and rotation;
  no in-app KMS; no master key to distribute; adapter code reads a plain file (single
  `Path.read_text()` call); webhook absence expressed as absent file (no sentinel value).
- **Cons:** backup = manual export per secret; no centralized audit trail (relies on Podman +
  host audit); recovery on a new host requires re-creating secrets from operator input.

### Option B: External secret manager (Vault, AWS Secrets Manager)

Bot tokens stored in Vault or a cloud secret manager; adapter containers call the API at
bootstrap with a Vault token or cloud IAM role.

- **Pros:** centralized audit log; RBAC out of the box; backup managed by the service.
- **Cons:** introduces an external network dependency at every adapter boot; requires Vault/IAM
  to be reachable before any bot can start; heavier ops burden on M₁ (single operator, no
  ops team); violates the ADR-068 axiom that backend single-host is acceptable — this would
  make credential access host-external by necessity.

### Option C: DB-encrypted `bot_secrets` table (status quo ante)

Retain or rebuild `CredentialStore` + `LyraKeyring` + `bot_secrets` in `config.db`.

- **Pros:** keeps credentials co-located with other config; SQL query surface familiar.
- **Cons:** recreates the exact layer #1057 removed: master key (`keyring.key`) still requires
  secure delivery to every adapter container; no per-secret rotation; DB-mount on adapter
  containers; coupling between the credential plane and the config.db schema.

## Decision

**Adopt Option A.** Two Podman secrets per bot — one for the bot token, one for the optional
webhook secret (χ-1 resolution: separate single-purpose secrets, not a packed JSON blob).

χ-1 rationale (from spec): single-purpose secrets match every existing secret in the Quadlet
ecosystem (raw bytes, no parser); avoids a JSON parser in the failure-loud bootstrap path;
allows independent rotation of token vs. webhook; nullable webhook expressed by omitting the
secret entirely rather than requiring a sentinel value.

### Secret naming convention

| Secret name | Content | Mount target |
|---|---|---|
| `lyra-bot-<platform>-<bot_id>` | raw bot token bytes | `/run/secrets/bot_token-<bot_id>` |
| `lyra-bot-<platform>-<bot_id>-webhook` | raw webhook secret bytes | `/run/secrets/bot_webhook-<bot_id>` (omitted if not configured) |

`uid=1500,gid=1500` on all `Secret=` lines — mirrors the existing `lyra-nkey-*` pattern;
adapter containers run under `UserNS=keep-id:uid=1500,gid=1500`.

### Adapter bootstrap

`adapter_standalone.py` reads `Path("/run/secrets/bot_token-" + bot_id).read_text().strip()`
at startup. File absence raises `BootstrapError` with the expected path — no fallback to
`config.db`. Webhook is read if present (`.exists()` check); absence is silent (matches the
pre-migration nullable behavior).

### Migration path

`lyra bot secret migrate` reads every `(platform, bot_id, token, webhook_secret)` row from
`~/.lyra/config.db:bot_secrets`, decrypts via the existing `LyraKeyring`, then calls
`podman secret create --replace` per row. Idempotent. On success prints a per-row table
`PLATFORM BOT_ID TOKEN_OK WEBHOOK_OK` and a summary `Migrated N tokens, M webhook secrets;
safe to drop bot_secrets table.` Once migration is confirmed on M₁, `CredentialStore` and
`bot_secrets` DDL are deleted (slice 3 of #1057).

## Consequences

### Positive

- Fits ADR-055 Quadlet credential-store pattern — bot secrets join nkeys and NATS auth tokens
  in the same `type=mount` Podman secret plane; no second credential mechanism.
- Per-bot rotation: `lyra bot secret install <platform> <bot_id>` + `make <svc> restart` —
  operator does not touch `config.db` or any encryption key.
- `config.db` mount is stripped from adapter `.container` files; adapters have no read access
  to the broader configuration DB (reduced blast radius on adapter container compromise).
- Adapter bootstrap is simpler: one `Path.read_text()` per bot vs. DB open + Fernet decrypt.
- `~/.lyra/keyring.key` is safe to remove once `LyraKeyring` has no remaining consumers (all
  adapter-path imports removed; any surviving consumers in `config.db` sibling stores must be
  documented in `src/lyra/infrastructure/CLAUDE.md` before deletion).

### Negative

- Backup story: manual. `podman secret inspect` returns metadata only; secret content requires
  a `podman secret export` equivalent or re-entry from the operator. No automated backup path
  in v1.
- Recovery on a new host requires re-creating each secret from operator input (token values
  must be re-fetched from the Telegram/Discord bot management dashboards).
- No centralized audit trail for secret reads. Host-level audit (Podman + Linux audit) is the
  only signal for "which process read which secret".

### Operational

- Each bot requires two `Secret=` lines in the platform adapter `.container` file (or a
  Makefile target `quadlet-bot-secrets-render` that emits them from `podman secret ls`).
- Quadlet validates `Secret=` references at container start; a missing secret causes a clear
  per-secret error, not a silent nil token.
- `lyra bot secret list` queries `podman secret ls --filter name=lyra-bot-` — single source of
  truth for provisioned bots once `bot_secrets` is dropped.
