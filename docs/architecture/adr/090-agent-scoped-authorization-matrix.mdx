## Status

Accepted — 2026-06-21

## Context

Factory authorization is **bot-centric** today:

- `BotRow` carries `owner_users`, `trusted_users`, `trusted_roles`, `default_trust`.
- `seed_grants_from_bots()` writes platform-prefixed grants into `auth.db`.
- Hub registers one `Authenticator` per `(platform, bot_id)`.
- `bot_agent_map` routes `(platform, bot_id) → agent_name`, but **no per-agent ACL** exists.

A user authorized on bot `lyra` (Telegram) automatically reaches whatever agent that bot
binds to. A user blocked on bot `aryl` (Discord) cannot reach the same agent even if bound
there too. Authorization is coupled to transport, not to the agent workspace.

Product direction requires **multi-tenant agents** within a single deployment: each agent is
a logical tenant with its own authorization matrix (users and/or roles). **Bots inherit**
effective access from the agent they bind to — bots remain transport endpoints, not
authorization SSoT.

Constraints inherited from prior decisions:

- **C3** (security-routing.md): adapters are untrusted normalizers; hub is authoritative
  for identity and authorization (#456 trust re-resolution).
- **ADR-049**: wire contracts live in `roxabi-contracts`; authorization data is not adapter
  wire payload.
- **ADR-1946 / #1946**: KV roster projections (`roster.telegram`, `roster.discord`,
  `roster.web`) carry transport fields only — never auth lists on the wire.
- **ADR-059**: ports in `factory.core`, SQLite in `factory.infrastructure`, wiring in
  bootstrap composition root.
- **ADR-073**: authorization is a hub pipeline stage — not adapter logic.

> **Naming:** "Multi-tenant agents" means **logical agent tenancy** inside one operator-owned
> instance. It does **not** change the deployment model (still single-instance, single
> operator per `docs/history/vision.md`). True multi-instance SaaS tenancy is out of scope.

## Options Considered

### Option A: Keep bot-centric auth; duplicate grants per bot

Copy the same `owner_users` onto every bot bound to agent `lyra_default`.

- **Pros:** No hub pipeline change; TG/DC adapters unchanged.
- **Cons:** Drift when bots diverge; operator burden scales with bot count; violates
  "bots inherit from agent"; no single matrix view per agent.

### Option B: Agent-scoped grant matrix in `auth.db`; hub enforces post-binding (chosen)

Introduce `agent_grants` (agent × principal × capability). Effective bot access =
authorize(user/roles, bound agent). Deprecate `BotRow` auth fields over migration slices.

- **Pros:** Single SSoT per agent; bots are thin transport; C3 preserved; aligns with
  identity aliases across platforms; KV roster stays auth-free.
- **Cons:** Hub middleware + schema work; migration from bot grants; pairing and web
  surfaces need agent-scoped evolution.

### Option C: Per-agent auth in `AgentStore` / agent TOML

Store ACL beside agent config (persona, tools).

- **Pros:** Co-located with agent definition.
- **Cons:** Mixes mutable runtime grants with relatively static agent config; harder to
  audit/revoke; `auth.db` already owns grants and pairing writes — splits SSoT.

### Option D: Authorization on NATS KV wire (per-agent roster keys)

Publish allowed principals in `factory-state` KV for adapters to enforce locally.

- **Pros:** Adapters could filter before NATS publish.
- **Cons:** Violates C3; leaks PII onto the bus; duplicates hub logic; contradicts #1946
  D3 (adapter projection excludes auth fields).

## Decision

**Option B** is adopted.

### 1. Agent = logical tenant

Each named agent (`lyra_default`, `legal_assistant`, …) owns an **authorization matrix**:

| Field | Meaning |
|-------|---------|
| `agent_name` | Tenant key (matches `AgentRow.name`) |
| `principal.kind` | `user` or `role` |
| `principal.id` | Stable string, e.g. `tg:user:7377831990`, `dc:user:…`, `dc:role:…` |
| `capability` | `use` (chat) or `admin` (configure / privileged commands) — **MVP grants `use` only; `admin` is a deferred follow-up** |

**Fail-safe:** no matching grant → **deny** (`use` not implied).

Global operators in `[admin].user_ids` retain bypass via existing admin resolution
(`Authenticator` / `is_admin`) until explicitly narrowed in a follow-up ADR.

### 2. Bots inherit from bound agent

```text
effective_agent(platform, bot_id) := bot_agent_map[(platform, bot_id)]

can_access_bot(msg) :=
  authorize(effective_agent(...), principals(msg)) == ALLOW
```

`BotRow` retains **transport-only** fields (`webhook_enabled`, `auto_thread`,
`thread_hot_hours`, token secret refs). Fields `owner_users`, `trusted_users`,
`trusted_roles`, `default_trust` are **deprecated** — migrated to `agent_grants`, then
removed from BotStore seed path.

`bot_agent_map` and hub bindings (`RoutingKey` + wildcard `*` for TG/DC) are unchanged.

### 3. SSoT and storage

| Data | SSoT | Notes |
|------|------|-------|
| Grant matrix | `auth.db` table `agent_grants` | Same DB as pairing grants |
| Bot → agent binding | `BotStore` / `bot_agent_map` | Unchanged |
| Adapter roster KV | `factory-state` | Names + transport only — no auth |
| Agent config | `AgentStore` | Persona/tools — not authorization |

Authorization **never** appears on NATS subjects or KV roster documents.

### 4. Core port (hexagonal)

New port in `factory.core.auth` (names indicative):

```python
class AgentAuthorizer(Protocol):
    def authorize(
        self,
        *,
        agent_name: str,
        user_id: str,
        roles: Sequence[str] = (),
    ) -> AuthDecision: ...
```

Implementation: `AgentGrantStore` in `factory.infrastructure.stores` (SQLite, `auth.db`).
Pure models (`Principal`, `AgentGrant`, `AuthDecision`) live in `factory.core.auth` with
no I/O.

Principal resolution can reuse `IdentityAliasStore.resolve_aliases()` so linked TG/DC
identities inherit grants on the canonical key. **Deferred for the MVP: grants are
platform-scoped (raw `tg:user:…` / `dc:user:…`); cross-platform alias resolution is a
follow-up** — a ban on one platform does not propagate to a linked identity on another
until aliasing lands.

Discord role grants use `dc:role:<snowflake>` principals; `msg.roles` is already present
on `InboundMessage` (C3).

### 5. Hub pipeline placement (ADR-073)

New stage **`AuthorizeAgentMiddleware`** immediately **after** `ResolveBindingMiddleware`
(stage 6 today — agent name known from binding).

```text
… → ResolveBinding → AuthorizeAgent → MessagePrep → Pool submit
```

Legacy `ResolveTrustMiddleware` + `TrustGuardMiddleware` were consolidated into
`ResolveIdentityMiddleware` (ban list + admin flag only) in #2114. Bot-level trust
no longer gates inbound chat — `agent_grants` is the sole access SSoT.

Denied messages use a **pull-model inline refusal** (not a push DM): the stage
short-circuits with a reply *in the originating channel* directing the user to the public
bot (e.g. "écris à @bot_public"), degrading to a pointer to factory.roxabi.dev when no
public bot is deployed on that platform. Unsolicited push direct-messages are **not**
attempted — Telegram prohibits bot-initiated DMs to users who never messaged the bot first
("Forbidden: bot can't initiate conversation") and Discord returns error 50007 when the
user has DMs disabled. A `MessageDropped(reason="agent_unauthorized")` audit event is still
emitted for observability.

> **Status (2026-06-27):** MVP shipped (epic #1980). `AuthorizeAgentMiddleware` runs at
> pipeline index 7 (immediately after `ResolveBindingMiddleware`), calls `AgentAuthorizer`,
> and on deny emits `MessageDropped(reason="agent_unauthorized")` plus an inline pull refusal
> using `BotRow.public_bot` / KV roster `RosterBotEntry.public_bot` when set, else
> factory.roxabi.dev. Operator CLI (`grant` / `revoke` / `auth list`) and UserStore SSOT
> landed in PR #2024. Post-MVP slices (dual-read, `migrate-bot-grants`, `admin`, alias) remain
> open under #1980.

### 6. Adapter impact (C3 preserved)

| Surface | Change |
|---------|--------|
| Telegram adapter | **None** — still forwards `trust_level=PUBLIC`, `user_id` |
| Discord adapter | **None** — still forwards `roles` |
| Web smoke / dashboard | **Future** — HTTP session auth supplies real `user_id`; agent picker
  filtered by `AgentAuthorizer`; localhost bind remains phase-1 deploy hardening only |
| NATS ACL | **None** — no new identities or KV grants |

### 7. Operator interface

CLI verbs (implementation slice, not blocking this ADR):

```bash
factory agent grant <agent> --user tg:user:<id> [--capability use|admin]
factory agent grant <agent> --role dc:role:<id> [--capability use|admin]
factory agent revoke <agent> --user tg:user:<id>
factory agent auth list <agent>
factory agent migrate-bot-grants   # one-shot BotRow → agent_grants (migration phase)
```

**MVP:** only `grant` / `revoke` / `auth list` with `--capability use` (the default);
`--capability admin` and `migrate-bot-grants` belong to later phases (see §8).

Pairing (`/join`) evolves to agent-scoped grants in a follow-up slice (code + grant on
validated agent, not platform-wide `TRUSTED` only).

### 8. Migration slices (execution order)

1. **Foundation** — schema `agent_grants`, `AgentAuthorizer`, `AuthorizeAgentMiddleware`,
   unit + middleware tests.
2. **Dual-read** — bot grants AND agent grants both honored (deny if neither allows).
3. **Migration CLI** — `migrate-bot-grants`, operator docs.
4. **Deprecation** — stop `seed_grants_from_bots`; BotRow auth fields read-only legacy.
5. **Surfaces** — agent-scoped pairing, web roster filter, remove legacy trust stages.
   **Status (2026-07-01):** slice 5 shipped (#2114) — `ResolveIdentityMiddleware`
   replaces the legacy trust pair; `AuthorizeAgentMiddleware` + `agent_grants` is the
   sole inbound access gate; admin bypass via `msg.is_admin`.

**MVP scope (epic #1980):** slice 1 (Foundation) + the operator CLI
(`grant` / `revoke` / `auth list`, `use` capability) + the pull-model refusal (§5) + the
public-agent default posture. Dual-read, `migrate-bot-grants`, deprecation, cross-platform
aliasing, and the `admin` capability are explicit later phases.

Each slice is an isolated PR; no big-bang cutover.

## Consequences

### Positive

- Authorization axis aligns with product mental model: **agent workspace**, not chat bot.
- One matrix per agent; N bots binding the same agent share identical access automatically.
- C3 and #1946 wire hygiene preserved — no auth on KV or adapter containers.
- Identity aliases enable cross-platform single grant.
- Clear extension point for web dashboard and future RBAC capabilities.

### Negative

- Short-term **dual SSoT** during migration (bot grants + agent grants) — must time-box.
- Operator workflow changes: grants move from `factory bot patch owner_users` to
  `factory agent grant`.
- Web phase 1 (`user_id="smoke"`, open roster) is intentionally permissive until slice 5.
- `TrustLevel` enum becomes legacy for inbound gating; capabilities are the long-term
  vocabulary.

### Neutral

- `docs/architecture/security-routing.md` `#auth` section will need a follow-up edit after
  slice 1 lands (mark bot-centric flow as superseded by this ADR).
- No `roxabi-contracts` change required unless a future audit event type records
  `agent_unauthorized` drops (optional, slice 1+).

## Key invariants

- Adapters **must not** enforce agent authorization — hub only.
- `agent_grants` **must not** be published to `factory-state` KV or NATS subjects.
- `AuthorizeAgentMiddleware` **must** run after binding resolution (agent name known).
- No grant for `(agent, principal, capability)` → **deny** (fail-safe).
- Bot effective access **must** derive from `bot_agent_map → agent_name`, not from
  parallel bot-local ACL once deprecation completes.
