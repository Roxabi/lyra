## Context

Derived from frame [999-stdout-only-logging-frame.mdx](../frames/999-stdout-only-logging-frame.mdx).

Lyra containers currently dual-write logs via `RotatingFileHandler` (named volume) + `StreamHandler` (stdout → journald). The file handler is redundant in the OCI/systemd runtime and couples application code to infrastructure concerns. This spec covers removing all file-handler machinery from lyra's Python entry points and deleting the `lyra-logs` Quadlet volume and its mounts.

## Goal

Remove `RotatingFileHandler` from all lyra entry points and delete the `lyra-logs` volume and its Quadlet mounts, so lyra logs exclusively to stdout (captured by journald in prod, redirectable to file in dev).

## Users

- **Primary:** ops/maintainer — accesses logs uniformly via `journalctl`; no orphaned volume to manage.
- **Secondary:** devs running lyra locally — use shell redirect (`lyra hub >> app.log 2>&1`) or a systemd user unit; no in-code log file path to maintain.

## Expected Behavior

After the change:

1. `lyra start`, `lyra hub`, `lyra adapter telegram/discord/clipool` all start without errors and emit logs only to stdout.
2. No file is written to `~/.local/state/lyra/logs/` by the app. The directory may or may not exist — the app neither creates nor writes to it.
3. Quadlet units (`lyra-hub`, `lyra-telegram`, `lyra-discord`, `lyra-clipool`) have no `Volume=lyra-logs.volume:…` line. `lyra-logs.volume` no longer exists in `deploy/quadlet/`.
4. `systemctl --user daemon-reload` after deploying the updated Quadlet files does not produce errors about `lyra-logs.volume`.
5. `lyra.monitoring` (cron health checks) logs to stdout only; `monitor.log` is not written.
6. `LYRA_LOG_DIR` env var is removed from `_setup_logging` (dead after file handler removal). Dev log redirect is handled at the shell level.
7. `LoggingConfig.json_file` field and any JSON file-formatter references are removed (dead config after file handler removal).
