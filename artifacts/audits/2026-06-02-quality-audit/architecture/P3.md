### Summary
P3 (messaging, pool, stores, memory) is largely clean: no runtime layer violations, no circular import chains, and no direct imports from adapters/llm/commands/infrastructure. Two medium issues: a deferred `importlib.import_module` workaround in the pool processor and SQL DDL embedded in a core config module.

### Recommendations
1. **Refactor processor registry to a driven port (P2, ~2h)** — Extract a narrow `ProcessorRegistryProtocol` or factory interface that `pool_processor_exec` can depend on at module level, eliminating the deferred `importlib.import_module` workaround. The registry can be injected at bootstrap.
2. **Move pairing SQL DDL to infrastructure (P2, ~1h)** — Move `_CREATE_PAIRING_CODES` and related schema constants to `lyra.infrastructure.stores.pairing` or a dedicated schema file. `pairing_config.py` should keep only `PairingConfig`, `PairingError`, and pure Python constants.
3. **Relocate `JsonAgentStore` to test utilities or infrastructure (P3, ~30m)** — Move the concrete JSON implementation to `tests/fakes/` or `lyra.infrastructure.stores` to align with the "protocols only" claim in `core/stores/__init__.py`.
4. **Normalize `_extract_worker_error` visibility (P3, ~15m)** — Either rename to `extract_worker_error` (public) or remove it from `__all__` and have consumers import directly from `messaging.utils.error_extractor`.
5. **Resolve `IdentityAliasStore` TYPE_CHECKING debt (P3, ~1h)** — Extract `IdentityAliasStoreProtocol` into `core/stores/` and have `memory.py` depend on that. Wire the concrete store at bootstrap.
