## Findings

| # | Severity | Location | Recommendation |
|---|----------|----------|----------------|
| F-1 | Info | `helper.py` MintError emit path | MintError carries the data needed to construct a `MintFailureEvent` envelope, but the helper does not yet wire a NATS publish. Hub-side subscriber (T17) is consumer-ready. Mint failures will not propagate until the publish path is wired. Track as a follow-up issue; T18 host-smoke RED-GATE will surface this gap empirically. Non-blocking for v1 ship — manual log inspection on host can substitute for the NATS event during the M₁ rollout. |
| F-2 | Low | `dispenser.py` socket-mode chmod ordering | `os.chmod(sock_path, 0o660)` runs after `start_unix_server`. Between bind (umask-default mode) and the chmod call, a connector with the wrong group could in theory race the server. Practical risk is near-zero (sub-microsecond window inside the asyncio constructor on the same process). If tightened, pre-set process umask to 0117 before bind, or atomic socket creation with explicit perms. Non-blocking. |

## Out-of-Scope Gaps Observed

- **MintError → MintFailureEvent NATS publish** — see Finding F-1. This is the producer side of the V6 alert path. T17 subscriber + contract envelope are in place; only the helper-side `nc.publish(SUBJECTS.gh_mint_failure(machine), serialize(event))` call is missing. Implementing it requires giving the helper its own NATS connection + nkey identity (the helper runs as uid 1501; the existing clipool nkey at `/run/secrets/clipool-worker.seed` is mode 0400 uid 1500 only). Two design options for follow-up: (a) issue a dedicated `lyra-gh.seed` per ADR-046 + mount with uid 1501, or (b) widen the clipool seed to gid 1502 and let both uids read it (smaller change, marginally weaker isolation). Recommend (a).

- **Refresh-loop bootstrap caller** — RESOLVED in `src/lyra/tools/gh_token/daemon.py` (commit incoming). `run_daemon` starts both `Dispenser.serve()` and `refresh_loop` concurrently in one asyncio task group, with env-driven config (`LYRA_GH_APP_ID` + `LYRA_GH_INSTALLATION_ID` + `LYRA_GH_PEM_PATH`). 6 unit tests cover config validation, socket bind, and stale-socket cleanup. Entrypoint is `python -m lyra.tools.gh_token.daemon`.

- **`lyra-gh-helper` Quadlet runtime wiring** — RESOLVED in this PR (option a: sidecar `.pod`). See `## Quadlet Sidecar Pod Design` section below.

- **MintError → MintFailureEvent NATS publish** — UNCHANGED. See Finding F-1 above. Independent of the Quadlet wiring decision.

## Quadlet Sidecar Pod Design (resolves audit gap #2)

### Pod topology

```
lyra-gh.pod (infra container — shared net/ipc namespace)
├── lyra-gh-helper.container   uid 1501 / gid 1502 (lyra-gh / lyra-tokenuser)
│     PEM secret (0400/1501) ──► python -m lyra.tools.gh_token.daemon
│     Tmpfs /run/lyra-gh-token (0710 / 1501:1502)
│         ├── token.json       0600 / 1501:1501  (unreadable to uid 1500)
│         └── dispenser.sock   0660 / 1501:1502  (reachable by uid 1500 via gid 1502)
│
└── lyra-clipool.container     uid 1500 / gid 1500 (lyra / lyra-tokenuser member)
      Tmpfs /run/lyra-gh-token (same path — Podman shares tmpfs between pod containers)
      lyra-gh shim ──► connect(dispenser.sock) ──► read token ──► exec env GH_TOKEN=… gh …
```

### File responsibilities

| File | Role |
|---|---|
| `lyra-gh.pod` | Pod: shared UserNS (`keep-id:uid=1500`), network, start-limit |
| `lyra-gh-helper.container` | Daemon: uid 1501, PEM secret, App ID inlined, `python -m lyra.tools.gh_token.daemon` |
| `lyra-clipool.container` | Worker: uid 1500, Pod=lyra-gh.pod, no PEM, no GH_APP_ID env |

### Why App ID is inlined (not in env file or DB)

- App ID + install_id are public, not secret — no reason to protect them via Podman secret or per-host file
- They are invariant across M₁/M₂ after the single-App (`lyra-harness`) decision (Decision Log 2026-05-06)
- Helper sidecar (uid 1501, ReadOnly=true) cannot read clipool's LyraKeyring SQLite (uid 1500) — pushing via NATS would be overkill for two static public strings
- Deployment binding belongs in the unit file (git-versioned, audit-trailed) — not runtime data (DB/keyring) nor Podman secret (reserved for actual credentials)
- Revisit trigger: a 2nd GitHub App is registered, OR BotIdentity registry lands per Phase 2 of the consensus mdx

### Mode 0710 traversal rationale

`/run/lyra-gh-token` dir: `mode=0710, uid=1501, gid=1502`

| Bit | Who | Effect |
|---|---|---|
| `rwx` (owner=1501) | helper daemon | full access: create token.json, bind socket |
| `--x` (group=1502) | uid 1500 (member gid 1502) | can `connect()` to socket path but **cannot `ls`** dir nor `cat` token.json |
| `---` (other) | everyone else | no access |

This is the minimum mode satisfying I-2 (token unreadable) + I-3 (socket reachable). The `x` bit grants traversal only — not read (`r`). A process needs `r` to list directory contents; the lyra-gh shim constructs the socket path explicitly.

### Pod-level Tmpfs= — verification result

**Pod-level `Tmpfs=` is NOT supported in any Podman version (4.9–5.x).**

- Podman 4.9.3 quadlet source (`/usr/libexec/podman/quadlet`, strings analysis): no `KeyTmpfs` in pod section.
- Podman 5.0 source (GitHub inspection): `supportedPodKeys` contains `Network`, `Volume`, `PublishPort`, `UserNS`, `PodName`, `PodmanArgs`, `GlobalArgs`, `ContainersConfModule` — no `Tmpfs`.
- **Decision**: both containers declare identical `Tmpfs=/run/lyra-gh-token:mode=0710,uid=1501,gid=1502`. Podman mounts the tmpfs into both containers' namespaces within the pod.

### Same-image constraint

Both containers use `Image=ghcr.io/roxabi/lyra:staging`. No separate `lyra-gh-helper:latest` build.

- uid 1501 (`lyra-gh`) + gid 1502 (`lyra-tokenuser`) are baked into the image at Dockerfile lines 49–51.
- `python -m lyra.tools.gh_token.daemon` entrypoint is in the same installed package.
- Build matrix stays simple: one image, two containers, different `User=` directives.
