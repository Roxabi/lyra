## Problem

Session resume and `/clear` are broken in the NATS clipool path. Two root causes:

1. `CliNatsDriver.link_lyra_session()` is a no-op — never stores the mapping — so `_build_cmd_payload` always sends `pool_id` instead of the real `lyra_session_id` UUID.
2. The `lyra_session_id → cli_session_id` mapping is owned by the clipool worker (via `CliPoolSessionMixin`), but the worker has no TurnStore in standalone or prod — so `_persist_cli_session` silently skips every turn and resume always cold-starts.

The deeper issue: clipool is a stateless CLI executor; it should not own session persistence. The hub is the router and session owner — it has TurnStore and already knows `lyra_session_id`. The mapping should live in the hub's TurnStore, written and read by the hub-side driver (`CliNatsDriver`), not by the worker.

## Who

- **Primary:** end users of the Telegram/Discord adapters who rely on session continuity (resume after reconnect, `/clear` to start fresh).
- **Secondary:** developers running clipool locally who observe silent session resets.

## Constraints

- No breaking contract changes — `CliCmdPayload` and `CliControlCmd` field names stay; semantics of `CliControlCmd.session_id` changes from lyra UUID to CLI session ID (documented, rename deferred to #1009).
- Fix must not break the local (non-NATS) CLI driver path.
- Clipool worker becomes fully stateless — no TurnStore, no `link_lyra_session`.
- `CliNatsDriver` runs in the hub process and has access to hub's TurnStore via injection.

## Out of Scope

- Renaming `CliControlCmd.session_id` to `cli_session_id` in the contract (#1009).
- Removing the `resume_and_reset` control command entirely (#1009).
- Removing `_lyra_sessions` from `CliPoolSessionMixin` once the local driver path is also migrated (#1009).
- Resume outcome logging / heartbeat counters (#1009).
- `lyra-data.volume` Quadlet wiring — no longer needed for clipool once this fix lands.
