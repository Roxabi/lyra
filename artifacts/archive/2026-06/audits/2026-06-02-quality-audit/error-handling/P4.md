### Summary
Two broad `except Exception` catches found in P4: one swallows unknown errors (and `CancelledError`) in `vault_add.py` (P1), one re-raises after event translation in `stream_processor.py` (P2). Network-bound calls in `vault_add.py` and `_scraping.py` lack retry logic (P3). No bare `except:`, no swallowed `pass` errors, no missing exception context.

### Findings

| P1 | src/lyra/core/processors/vault_add.py | 97 | `except Exception as exc:` (noqa: BLE001) swallows **all** non-`VaultWriteFailed` exceptions, including `asyncio.CancelledError` and programming errors. Logs with `exc_info=True` but does **not** re-raise, so task cancellation is silently absorbed and the user only sees a generic "Vault write failed" note. |

| P3 | src/lyra/core/processors/vault_add.py | 88 | `await self.tools.vault.add(...)` is a network-bound call with no retry/backoff logic. Transient failures (timeout, brief NATS/JetStream unavailability) will surface to the user as permanent errors even though a single retry might succeed. |
| P3 | src/lyra/core/processors/_scraping.py | 99 | `await scraper.scrape(url, timeout=30.0)` is a network-bound call with no retry/backoff logic. The caller has a `ScrapeFailed` fallback, but transient network errors are treated as terminal failures without retry. |

### Recommendations (prioritized, with effort estimate)

1. **Narrow `vault_add.py` broad catch and re-raise cancellation** (P1, ~15 min)
   - Replace `except Exception` with `except VaultWriteFailed` for the specific domain error, then a separate `except Exception` that logs and re-raises (or at least explicitly re-raises `asyncio.CancelledError` / `BaseException` subclasses before the broad catch).
   - This fixes the swallowed-cancellation bug and ensures programming errors are not silently hidden.

2. **Add `except asyncio.CancelledError` bypass to `stream_processor.py`** (P2, ~10 min)
   - Before the broad `except Exception` in `process()`, add an `except asyncio.CancelledError: raise` guard so cancellation is not translated into `RunErrorRenderEvent` and routed through the error pipeline.

3. **Evaluate retry wrappers for processor network calls** (P3, ~30 min)
   - `vault.add()` and `scraper.scrape()` are transient-prone. If the project already uses `tenacity` or a custom retry decorator in `lyra.transport`, apply it here. If not, consider adding a lightweight `async_retry` helper for processor-level network calls (factor=2, max 3 retries, exceptions: `TimeoutError`, `ConnectionError`, `NatsError`).
