## Problem

Three disjoint stores hold "last session per pool"; the two adapter mirrors are never cleared by
`/clear` → resurrection. `turns.db` `pool_sessions` is already canonical and self-heals. (Full
problem statement: the frame.)

## Outcome

`turns.db` `pool_sessions` is the **sole** SSoT for Shape-A last-session; adapters hold nothing for
resume; `/clear` is genuinely fresh; reply-to (path-1) survives `/clear`; the `LastSessionStore`
port is collapsed. No regression in resume for Telegram DM, Discord DM, or Discord threads.

## Appetite

One focused cycle. The change is **predominantly deletion** (path-2, two store surfaces, one port)
+ one additive migration (`cwd` reservation). No new subsystems.

### Drift corrections to the design doc (job-model-concept-analysis.md §8–11)

1. **Q7 wording** — the KvLastSessionStore branch is **not** in `_build_thread_path`; it's in a
   separate `_build_last_session_path` (Telegram + Discord DM). `_build_thread_path` (Discord
   threads) holds the **ThreadStore `update_session`** write-back (that's the Q8/D3 target). So the
   inbound change is *two* deletions: delete `_build_last_session_path` (path-2 KV) **and** strip the
   ThreadStore session-pointer read/write from `_build_thread_path`.
2. **Discord-thread routing** — after path-2 removal, Discord threads must **not** be routed through
   `_build_last_session_path` (that IS path-2, deleted); they resume **hub-side via path-3** using
   the already-wired `scope_id=thread:{thread_id}` pool_id. No adapter-side lookup remains.

## Open decision — FRESH-status notification (BLOCKER, product/UX)

`ResumeStatus.FRESH` is returned **only** when path-2 was attempted-but-rejected
(`path_validation.py:52`). `middleware_submit.py:117` reacts to FRESH by calling
`_notify_session_fallthrough` → `try_notify_user` → a **real platform message**
(`SESSION_FALLTHROUGH_MSG`: "couldn't resume your previous session, starting fresh"). Removing
path-2 makes FRESH unreachable and silently drops this user-facing notice.

```
── Decision: FRESH-status notification after path-2 removal ──
Context:  FRESH only fired on path-2 reject; it drives a real "starting fresh" user notice.
          Post-#1777 the mirror-divergence that triggered it no longer exists; genuine
          "couldn't resume a dead session" detection is #1805/F2 scope.
Target:   no silent UX regression; keep #1777 clean.

Options:
  1. Drop the notice in #1777; document the behavior change; re-introduce a proper
     "couldn't resume → fresh" notice in #1805 where dead-resume detection lives   ← recommended
  2. Re-trigger the notice on a new path-3 condition now (requires resume-failure
     detection = #1805 scope pulled forward into #1777)
  3. Keep FRESH in the enum, repurpose its meaning (deferred semantics)
Recommended: Option 1 — the notice was a band-aid for the mirror we're deleting; proper
             fresh-fallback UX belongs with #1805's --resume-failure detection.
```

## Sub-decision — ThreadStore session-pointer columns

Dropping `session_id`/`pool_id` columns from `discord.db` needs SQLite ≥3.35 `DROP COLUMN`
(destructive, version-gated). Recommended: **stop reading/writing them, leave the columns dead**
(additive-only schema philosophy — same as the `try/except ADD COLUMN` pattern). A later cleanup
can drop them. → bake into spec; no DROP migration in #1777.

## Risks

- **FRESH notification** (blocker above) — must be decided before path_validation finalization.
- **Atomicity**: `ThreadSession` removal touches 6 files; KvLastSessionStore wiring touches the
  adapter ctor signatures — must land together or startup import errors cascade.
- **Telegram/DM resume coverage**: after path-2 removal, Telegram DMs rely solely on path-3
  (`get_last_session(pool_id)`). Verify `telegram:bot:scope` pool_id is stable across reconnects.
- **Test fixtures**: sweep for `ResumeStatus.FRESH` assertions, `ThreadStoreProtocol` fakes
  implementing `update_session`, and direct `KvLastSessionStore`/`ensure_kv` imports.
- **Migration string-match**: v5 reuses the `'duplicate column' in str(exc)` guard — fine, matches
  the proven v4 pattern.

## Test targets (regression)

- Telegram pool_id round-trip → path-3 returns prior session from turns.db (not KV).
- Discord thread resume via path-3 (`discord:bot:{id}:thread:{tid}`), no `retrieve_thread_session`.
- Discord DM resume via path-3.
- **path-1 survives `/clear`**: reply to pre-clear message resumes via MessageIndex, not turns.db.
- `/clear` self-heal: new session_id in pool_sessions; old no longer returned by get_last_session.
- FRESH→SKIPPED guard: Telegram DM no-prior-session → SKIPPED; `_notify_session_fallthrough` NOT called.
- ThreadStore ownership (`claim`/`is_owned`/`get_thread_ids`/`release`) intact post-removal.
- `get_session_pool_id` dead-code: pyright clean; no callers.
- `factory-turns-meta` bucket not provisioned at startup.

## Fit Check — recommended sequencing

The shape is **locked (D1 ownership consolidation)** — no alternative architecture in play; the
genuine choices are the FRESH decision (above) and column-drop-vs-dead (above). Recommended single
PR, applied in change-map order (deletions bottom-up: KV store → path-2 → store surfaces → port →
migration), so the suite stays green at each layer. Eliminated alternative: the "add `clear` to
both mirrors" patch (frame's simplest-alternative) — leaves the duplication, strictly worse.
