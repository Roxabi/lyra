### Summary
Partition P6 (Bootstrap, plugin commands) shows a clean security posture: no eval/exec, no pickle, no unsafe yaml.load, no shell injection, and no hardcoded secrets. All subprocess calls use hardcoded arg lists or safe validation. One low-severity defense-in-depth gap exists: `credentials.load_bot_token()` does not validate `bot_id` locally before constructing a filesystem path, relying solely on upstream validation.

### Findings
| severity | file | line | description |
|---|------|------|-------------|
| P3 | src/lyra/bootstrap/credentials.py | 48 | `load_bot_token()` constructs `tok_path = base / f"bot_token-{bot_id}"` without validating `bot_id` against a safe identifier pattern. Upstream validation exists in `agent_cmd/bots/init.py` (`_BOT_ID_RE = r"^[A-Za-z0-9_-]+$"`), but the credentials module does not enforce the invariant locally. A malicious `bot_id` reaching this function (e.g., via direct database tampering or a seed-path bypass) could traverse outside the secrets directory. |

### Recommendations
1. **Validate `bot_id` in `credentials.load_bot_token()`** — Re-use the `_BOT_ID_RE` pattern (`^[A-Za-z0-9_-]+$`) already defined in `agent_cmd/bots/init.py`. Raise `ValueError` early if `bot_id` does not match, turning a potential path traversal into a hard failure at the boundary.
2. **Consider exporting `bot_id` validation regex** to a shared constant (e.g., `lyra.core.constants.VALID_BOT_ID_RE`) so both the CLI seed path and the credential loader share the same invariant, preventing future drift.
3. **No other action required** — Subprocess usage (`embedded_nats.py`, `git_ownership_probe.py`, `systemctl.py`) is safe (hardcoded arg lists, no `shell=True`). TOML parsing uses `tomllib.load` (safe). SQLite interpolation uses parameterized queries and `_IDENT_RE` validation. Health endpoint uses `hmac.compare_digest`. Bot tokens are read from `/run/secrets` with defense-in-depth (env override ignored in production).
