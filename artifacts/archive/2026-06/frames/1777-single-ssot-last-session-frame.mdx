## Problem

`/clear` is broken because there are **three disjoint sources of truth** for "the last session of
a pool", written by three processes and read by three resume paths. The 2026-06-05 P0 inbound
outage (#1721, colon-key) surfaced the smell.

| Store | Backend | Writer | Read by (path) | Cleared by `/clear`? |
|---|---|---|---|---|
| `pool_sessions` | `turns.db` SQLite | turn-writer (ADR-075, **sole writer**) | hub — **path-3** | ✅ self-heals via `start_session` INSERT |
| `KvLastSessionStore` | NATS-KV `factory-turns-meta` | **adapter** (Telegram/DM) | adapter → `thread_session_id` → hub — **path-2** | ❌ stale → **resurrection** |
| `ThreadStore.session_pointer` | `discord.db` | **adapter** (Discord thread) | adapter — **path-2** | ❌ stale |

`turns.db` is **already canonical and self-healing** — the real SSoT was never wrong. The two
**adapter mirrors are the liars**: `/clear` rotates the in-memory session UUID and publishes
`start_session` but clears **no store** (the `LastSessionStore` port has only get/set, no delete);
because path-2 sits *above* path-3, the stale mirror **resurrects the cleared session**. Removing
the path-2 mirror fixes `/clear` with no new clearing logic on `turns.db`.

`MessageIndex` KV (msg→session, **path-1** reply-to) is a **separate fact**, not a last-session
duplicate — it stays.

## Who

- **Primary:** bot users (Telegram / Discord / CLI) — `/clear` silently resurrects the old
  session; reply-to resume is non-deterministic when contradicted by a stale mirror.
- **Secondary:** ops — currently hand-patch divergence (e.g. the `cp -n` rename fix on M₁).

## Constraints

- **ADR-075** — turn-writer is the **sole writer** of `turns.db`; hub mounts it read-only, adapter
  can't write it at all. Consolidation must respect this asymmetry.
- **Process split** — adapter and hub are separate processes in prod NATS mode (why the mirror
  exists at all).
- **Layering** — `core` must not import `infrastructure`; the resolved read-path is
  `TurnStoreProtocol.get_last_session()` (a driven port already held by core).
- **Axial-review mandatory** — the ADR crosses `inbound/` ↔ `core/` ↔ `infrastructure/`
  (`dev-core:axial-adr-review`); must also reconcile **ADR-073** (stage-axis per-stage contexts).
- **Colon-safe KV keys** — surviving path-1 keys must round-trip `telegram:bot:scope` ids
  (#1721 class).

## Out of Scope

Split to **#1805** (F2-extension, child of #1778) — architecturally orthogonal, must not gate the
SSoT bug-fix:

- CLI `--resume` failure → fresh-session fallback (Q10 / Fork F2).
- `cwd`-per-session materialization state + the `lyra→factory` one-time rename migration (orig
  item 3c) + Telegram `/folder` command + its security allowlist bound.

This frame **only reserves a nullable `cwd` column** on the session record so #1805 can land
without a second schema migration.

Also out of scope: the #1778 in-process JobContext carrier (blocked by #1619 WorkEnvelope); the
#475/#493 rule engine. #1777 ships **first and independently** (locked decision D4).

## Premise Validity

**Success in 6 months:** One documented SSoT for last-session-per-pool — the SSoT-consolidation
ADR is merged and passed axial-review; `/clear` followed by any message starts a genuinely fresh
session (no resurrection via any path); replying to bot message M deterministically resumes M's
session on both Telegram and Discord; no adapter writes a resume session-pointer anymore.

**Failure in 6 months (falsifiable):** After ship, we observe ≥1 recurrence of "cleared session
resurrected" **or** "non-deterministic reply-to resume" incident within a release cycle, **OR**
grep shows an adapter still writes a last-session pointer (`KvLastSessionStore` resume use or
`ThreadStore` session-pointer still present) — i.e. the consolidation was cosmetic and the
duplication survives.

**Simplest alternative:** Keep all three stores; add `clear_last_session()` to the port + both
mirror impls; have `reset_session()` cascade-clear all three.
**Why not simplest:** It leaves two adapter writers + two readers that can still diverge; every
`/clear` must clear **all three** stores correctly (miss one → resurrection returns); it preserves
a redundant port abstraction with no second implementation. The root duplication remains, so the
next divergence is a matter of time. Removing the mirrors (turns.db is already correct) is both
smaller and strictly more robust.

## Scope — locked design (from `job-model-concept-analysis.md` §8–11)

Decisions D1–D4 locked; Q6–Q8 resolved (architectural); Q9 ratified (product); Q10 deferred to
#1805.

- **D1 / path-2 removal** — drop `KvLastSessionStore` from the resume path (keep it only for
  `message_index` / path-1); after this, `turns.db` `pool_sessions` is the sole Shape-A
  last-session SSoT, `get_last_session(pool_id)` the only query.
- **Q7** — simplify `inbound/session_builder._build_thread_path` to pool-owned-only routing;
  remove the `KvLastSessionStore` resume branch.
- **Q8 / D3** — `ThreadStore` keeps `claim`, drops `update_session` + the session-pointer field
  (Discord thread = its own pool, `scope_id = thread:{thread_id}` → path-3 handles thread resume).
- **Q6 / J3** — **collapse the `LastSessionStore` port**; `core` calls
  `turn_store.get_last_session()` directly (it already holds `TurnStoreProtocol`). Removes dead
  set/clear surface; no second implementation = no indirection.
- **`/clear`** — works for free once path-2 is gone (turns.db self-heals); no new clear method.
- **F1 / Q9 (ratified): Option 3** — explicit reply-to (path-1) **survives `/clear`**; zero schema
  change. (`/clear` invalidates last-active only; reply-to + post-D3 thread-scope unaffected.)
- **Anticipatory** — reserve a nullable `cwd` column when touching the session record (unblocks
  #1805 without a second migration).
- **ADR + regression test** — `telegram:bot:scope` pool_id round-trips through all *surviving*
  resume paths (path-1 reply-to, path-3 last-active).
