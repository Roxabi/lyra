## Status

Accepted

## Context

Issue [#1061](https://github.com/Roxabi/lyra/issues/1061) was originally framed as *"NATS Object Store for large binary payloads"* — the goal being to stop pushing audio bytes inline through NATS messages (50 MB JetStream ceiling, base64 overhead, hub memory spikes per audio exchange).

During brainstorming the scope expanded to **all** Telegram + Discord attachments (documents, images, videos, voice, stickers, animations, GIFs) plus STT/TTS audio, with **permanent retention** ("store everything for now — disk space handled later — need data to train and test and debug"). This is no longer a transport/cache problem; it's a multi-modal asset archive problem.

Cross-checked with `dev-core:architect` and `dev-core:devops` 2nd-opinion reviews. Both reject NATS Object Store for unbounded archive growth:

- NATS Object Store is JetStream-backed; chunks live in a regular stream subject to standard limits (`max_bytes`, `max_age`). Without a cap, the stream grows without bound on the `store_dir` volume.
- No automatic compaction, no tiered storage, no native content-addressed dedup, no external query index.
- ML/debug tooling (DuckDB, pandas, S3-compatible CLI, parquet) has zero native path to a NATS Object Store. Reading the archive requires a NATS client.
- Mixing hot-path traffic (audio, sub-second roundtrip) with cold-path archive (training data, forever) on the same JetStream `store_dir` couples ops concerns that should be separated.

Additional constraints surfaced during the interview:

- **Telegram URL race:** `getFile` returns a bot-token-bound URL valid ≥1h only; lazy-fetch at consumer is unsafe → adapter must download eagerly at ingress.
- **Discord URL expiry:** CDN URLs are signed (`?ex=…&is=…&hm=…`) and expire ~24h; refresh requires re-fetching the message via bot API.
- **Single-host topology today:** all current workloads (hub, STT, TTS) run on `roxabituwer` (M₁). Cross-host transport is not a current requirement.
- **`audio_b64` / `audio_bytes` already inline** in `roxabi-contracts` — these need a deprecation path.

## Options Considered

### Option A: Single NATS bucket `lyra-blobs` (original #1061 framing)

- **Pros:** One abstraction; fits existing `roxabi-nats` SDK shape; one Quadlet primitive.
- **Cons:** JetStream stream grows without bound; no content search; no dedup; ML/debug locked to NATS clients; mixes hot+cold on same `store_dir`.

### Option B: Per-domain NATS buckets (`lyra-audio`, `lyra-files`, `lyra-images`)

- **Pros:** Cleaner per-type retention/access policies.
- **Cons:** Same JetStream cold-tier problem; more buckets to manage; cross-type dedup harder.

### Option C: Two-tier — NATS hot (≤24h) + MinIO/S3 archive

- **Pros:** Each tool used for its strength; ML/debug uses standard S3 tooling.
- **Cons:** 2 primitives + an archiver worker; copy-window data-loss risk; hub still pays NATS-OS latency on hot reads (~10–30 ms vs ~2–8 ms for direct MinIO at 5 MB); over-engineered for current single-host scale.

### Option D: MinIO direct (skip NATS Object Store entirely)

- **Pros:** One primitive; survives multi-host transition without re-architecture; presigned URLs / bucket policies available if ever needed; dedup possible via content-hash key scheme.
- **Cons:** Quadlet unit + readiness probe + S3 client in every worker + credential management for benefits that don't apply yet (all consumers are internal Python workers on a single host).

### Option E: Flat FS + SQLite — direct (no abstraction)

- **Pros:** Zero ops weight; native dedup via SHA-256; trivially backed up via rsync; queryable with `sqlite3`.
- **Cons:** Locks every adapter/worker to filesystem semantics; future migration to S3 = call-site rewrites in many places.

### Option F: Flat FS + SQLite **behind a `BlobStore` interface** ← chosen

- **Pros:** Zero-ops backend for v1; abstraction (3 methods: `put` / `get` / `exists`) isolates adapters/workers from the backing store; SHA-addressed layout makes future migration to MinIO/S3 a bulk copy + index re-import; no NATS-OS bloat; no JetStream archive coupling.
- **Cons:** A small abstraction layer eaten upfront; single-host-only until impl is swapped; loss model must be made explicit (no replication in v1).

## Decision

**Adopt Option F.** Introduce a `BlobStore` interface and a content-addressed flat-FS + SQLite implementation as v1.

### Interface

```python
class BlobStore(Protocol):
    async def put(self, data: bytes, *, mime: str, source: str,
                  filename: str | None = None,
                  platform_ref: str | None = None,
                  platform_message_id: str | None = None) -> BlobRef: ...
    async def get(self, store_key: str) -> bytes: ...
    async def exists(self, content_hash: str) -> BlobRef | None: ...
```

### `BlobRef` envelope (in `roxabi-contracts`)

```python
class BlobRef(BaseModel):
    store_key: str           # opaque to consumer; FS path or s3://... in future
    content_hash: str        # sha256 hex (dedup key)
    mime: str
    size: int
    filename: str | None     # nullable for synthesized audio
    source: Literal["telegram", "discord", "tts", "stt", ...]
    platform_ref: str | None         # "tg:<file_id>" | "discord:<ch>/<msg>/<att>" — recovery handle
    platform_message_id: str | None  # distinct from platform_ref; reconstructs conversation thread
    created_at: datetime             # mandatory: ML provenance, audit, future TTL gating
```

### v1 implementation

- **Package home:** new uv-workspace member `packages/roxabi-blobs/` (alongside existing `roxabi-nats`, `roxabi-contracts`). Whether to extract the workspace into a standalone shared repo for voiceCLI/imageCLI/llmCLI is a separate ecosystem decision.
- **Layout:** `/data/lyra/blobs/<sha[:2]>/<sha>` on a dedicated bind-mounted host path (SHA-256-addressed; sharded by 2-char prefix → 256 dirs; sufficient through ~5M blobs per devops sizing). Bind-mount over Podman named volume to avoid overlay2 CoW on the blob files.
- **Index:** SQLite at `/data/lyra/blobs/index.sqlite`. **Schema split** (per Q2 resolution):
  ```
  blobs       (content_hash PK, mime, size, store_path, first_seen_at)
  blob_refs   (id PK, content_hash FK, source, platform_ref,
               platform_message_id, filename, ingested_at)
  ```
  Many `blob_refs` rows → one `blobs` row (native dedup + per-ingestion provenance).
- **Dedup:** `put()` computes `sha256` first; if `blobs.content_hash` exists, bytes are not rewritten — only a new `blob_refs` row is appended.
- **Write ordering (durability):** write blob file → `fsync` → INSERT into `blob_refs` (and `blobs` if first sighting). Reverse order risks dangling index rows on crash. SQLite WAL mode mandatory.
- **No inline-threshold (per Q3 resolution):** every binary is content-addressed regardless of size. Text, emoji entities, and reaction metadata are out-of-scope for `BlobStore` — they travel as NATS message fields (plain JSON), as they already do.
- **GC interface designed in v1, retain-all policy:** `BlobStore.delete(blob_ref_id)` shape defined; reference-count check on `blobs.content_hash` before unlinking the file. Policy in v1 = never call delete; interface exists so future retention/quota policies don't require schema migration.
- **Mount options:** `noatime` on the blob mount (ext4 atime updates thrash replay/debug workloads).
- **v1 host:** FsBlobStore single-host on `lyra-hub` role (M₁); exposed via HTTP service (issue #1068 V7 ops + new V8 issue) for cross-host clients implementing the Protocol. Direct-FS access is reserved for co-located writers only (telegram_normalize, hub middleware). Cross-process via NATS message carrying `BlobRef`; raw bytes never traverse NATS.
- **Eager download at adapter ingress** for Telegram/Discord (URL-race avoidance). Hub never handles raw bytes for inbound files.
- **Deprecation policy (per Q4 resolution):** atomic migration — `audio_b64` / `audio_bytes` removed from `SttRequest`, `TtsResponse`, `AudioPayload` in the same epic. No `DeprecationWarning` shim. Coordinated PRs across `roxabi-contracts` → voiceCLI workers → lyra adapters.

### v1 ops contract

- **Storage volume:** dedicated mount (e.g., `/data/lyra/blobs`), not OS disk — isolates growth from OS health. Bind-mounted into containers (¬Podman named volume — avoids overlay2 CoW overhead on blob files).
- **Loss model is explicit:** v1 = single-host, no replication, loss tolerated. Documented here so it cannot become implicit.
- **Alerts before flipping permanent retention on:** inode utilization + disk-usage thresholds at 80%. Per devops sizing on ext4 default (1 inode / 16 KB), a 100 GB mount = ~6.5M inodes — not a near-term concern, but worth alerting.
- **Backups:** out of scope for v1 as a fresh task, but **atomicity required if backup is later added** — SQLite `.backup` API or WAL checkpoint before FS snapshot. Naive `tar` of FS + DB while live = inconsistent backup. Document in ops runbook before flipping any backup cron on.
- **Mount options:** `noatime` mandatory; `nodiratime` recommended.

### Migration path

When multi-host transport becomes a requirement (or when access control / presigned URLs / off-host replication are needed), the FS implementation is swapped for an S3/MinIO implementation behind the same `BlobStore` interface. Migration data path: SHA-addressed flat tree → `aws s3 sync` (or equivalent) into a content-hash-keyed bucket; SQLite index re-imported as object metadata. Adapter and worker call sites are unchanged.

#### Triggers for (b) HTTP-fronted FsBlobStore → (a) MinIO swap (any-of)

- Disk utilization >70% on `lyra-hub` blobstore volume (growth pressure requires distributed storage)
- HA requirement for blob availability (FsBlobStore single-host is not acceptable)
- ML/computer-vision workflow demanding S3-compatible API natively

Pre-trigger: the `source` field on `BlobRef` acts as a tier hint enabling a future scratch/archive tier split without contract change (see `BlobRef` schema above).

## HTTP service deployment design (Phase 1)

Per ADR-068 Ecosystem Service Plane, the v1 `FsBlobStore` backend is fronted by a dedicated HTTP service for ecosystem-transparent access. Deployment topology committed 2026-05-24.

### Container topology

- **Unit:** dedicated Quadlet `lyra-blobstore.container` (NOT embedded in `lyra-hub` process). Independent lifecycle, failure isolation, prepares MinIO swap.
- **Host role:** `lyra-hub` (M₁ today). Backend remains single-host until a Migration path trigger fires.
- **Image:** `ghcr.io/roxabi/lyra:<version>` invoked with a `lyra blobstore serve` subcommand.
  - Rationale: zero-overhead in Phase 1 — image is already pulled on M₁ for hub/adapters; shares `roxabi-contracts` version pinning automatically (no skew risk); CI pipeline already in place.
  - Migration trigger to dedicated image (`ghcr.io/roxabi/blobstore`): Protocol v2 stabilized (post-#1334) AND ≥3 consumers cross-repo (voice + image + llm). Three-strikes rule before extraction.
- **Framework:** FastAPI + uvicorn. Already in `pyproject.toml`; existing usage in `src/lyra/adapters/telegram/telegram.py` (webhook) and `src/lyra/bootstrap/infra/health.py` (health endpoint). Pydantic v2 native = aligned with `roxabi-contracts`.
- **Port:** TCP `8449` (chosen contiguous to `8443` hub-health; ¬conflict). Same port for internal Quadlet network and Tailnet exposure.
- **Host data dir:** `~/.lyra/blobs/` (grandfathered per CLI convention — `feedback_tool_data_dirs_grandfathered`). Bind-mounted into the container at `/data/lyra/blobs/` (matches §v1 implementation paths).
- **Host env file:** `~/.roxabi/lyra/env/blobstore.env` (Quadlet env convention — container-deployment-standard.md S7; distinct from data dir).
- **Networking:**
  - Same-host clients (hub, adapters, clipool) reach `http://lyra-blobstore:8449` via Quadlet network DNS.
  - Cross-host clients (M₂ workers) reach `http://roxabituwer.goose-logarithm.ts.net:8449` via Tailnet (`PublishPort=8449:8449`).
- **Startup ordering:** `After=lyra-blobstore.service` + `Wants=` on `lyra-hub` and adapter units. `HttpBlobStore` clients also retry on connect with bounded backoff for graceful boot.

### Wiring per process

| Process | BlobStore impl | URL |
|---|---|---|
| `lyra-blobstore` (the service) | `FsBlobStore` direct (in-process) | — |
| `lyra-hub`, `lyra-telegram`, `lyra-discord`, `lyra-clipool` | `HttpBlobStore` | `http://lyra-blobstore:8449` |
| voiceCLI workers (M₂) | `HttpBlobStore` | `http://roxabituwer.goose-logarithm.ts.net:8449` |
| imageCLI / llm-worker (M₂) | `HttpBlobStore` | idem |

All consumers speak the same `BlobStore` Protocol; the concrete impl is injected at bootstrap.

### HTTP API (Protocol mapping)

| Protocol method | HTTP endpoint | Body / Return |
|---|---|---|
| `put(bytes, mime?, ...)` → `BlobRef` | `PUT /blobs` (Content-Type: mime) | body=bytes → `{store_key, content_hash, size, dedup: bool, …}` |
| `get(store_key)` → bytes | `GET /blobs/<store_key>` | streams response body |
| `exists(store_key)` → bool | `HEAD /blobs/<store_key>` | 200 / 404 |
| `delete(store_key)` | `DELETE /blobs/<store_key>` | 204 |
| (v2 — #1334) `put_multipart(stream)` | `POST /blobs/multipart` + `PUT /blobs/multipart/<id>/<part>` + `POST /blobs/multipart/<id>/complete` | S3-compat multipart flow |
| (v2 — #1334) `get_stream(store_key)` | `GET /blobs/<store_key>` with `Range:` header support | chunked transfer |
| Health | `GET /healthz` | `{status, disk_used_pct, blob_count}` |
| Metrics | `GET /metrics` | Prometheus format — `disk_used_pct` gauge feeds MinIO swap trigger (>70%) |

Per ADR-068, `store_key` is opaque to the client: never assume FS-path semantics. URL-encoded as path segment.

### Backup (Phase 1)

- **Strategy:** Restic → Cloudflare R2 (encrypted, dedup, off-site, cheap). Daily cron on M₁.
- **Atomicity:** `index.sqlite` MUST be backed up via SQLite `.backup` API (or WAL checkpoint) BEFORE the FS snapshot. Naive `tar` of live FS + DB = inconsistent backup (see "Open questions / known gaps" in storage.md).
- **Syncthing:** `~/.lyra/blobs/` is excluded — content-addressed payload doesn't benefit from real-time replication, and volume is too large.

## Auth plane — Phase 1 (shared bearer) → Phase 2 (per-identity)

### Phase 1 — shared bearer token

- **Mechanism:** single shared bearer token. HTTP header `Authorization: Bearer <tok>`.
- **Storage:** Podman secret `lyra_blobstore_token`, `type=mount` (per ADR-054 secret hardening — NOT `type=env`).
- **Rotation:** manual via `podman secret create` + `systemctl --user restart lyra-blobstore.service`.
- **Audit (Phase-2-compatible from day one):** blobstore emits `{subject, op, store_key, ts, result}` to `LYRA_AUDIT` JetStream stream (β pattern, ADR-068). Phase 1 emits `subject = "service:<token_holder>"`; Phase 2 emits real `agent/<id>` or `user/<id>` — no schema change at the boundary.
- **Limitations** (acceptable for Phase 1, trigger for Phase 2 if violated):
  - No per-identity scoping (read = write, all blobs accessible to any token-holder).
  - No per-{agent, user} audit attribution (only the service is identified).
  - No quota per identity.

### Phase 2 — per-identity tokens & scoped grants (deferred, design committed)

**Trigger conditions** (any-of):
- Agents own user-uploaded blobs and cross-agent read isolation is required.
- Per-{agent, user} audit trail of blob access is required (compliance, debugging).
- Untrusted third-party consumers join the Tailnet and need bounded access.
- Quota enforcement per identity is required.

**Token model** (pick one at implementation time; both compatible with the Phase 1 `Authorization: Bearer <tok>` header — server-side upgrade only):

| Backend | Verification | Revocation | Best for |
|---|---|---|---|
| **JWT HS256** (claims: `sub`, `scope`, `prefix`, `iat`, `exp`) | stateless (shared secret) | denylist + short TTL + refresh | cross-machine without DB hit |
| **`~/.lyra/auth.db` lookup** (aligned with project `CLAUDE.md` `A := ~/.lyra/auth.db` grants/identity) | SQLite query per request (cheap WAL; ≤1k rps OK) | instant (delete row) | aligns with existing Lyra identity model |

Recommendation: **`auth.db` lookup** if Lyra continues brokering identity via `auth.db` for adapters; **JWT** if blobstore needs verification without `auth.db` access (e.g., deployed off-M₁).

**Scoping model:**

- **Dimensions:** `read | write | delete` × prefix-or-blob-bound (e.g., `agent/<id>/*`).
- **Token issuance:** handled by `lyra-hub` (or a dedicated auth service later). Endpoint shape:
  ```
  POST /auth/blob-token
    body: { subject: "agent/<id>" | "user/<id>",
            scope: ["read", "write"],
            prefix?: "agent/<id>/*",
            ttl?: "1h" }
    → { token: "<bearer>" }
  ```
- **Server-side enforcement:** blobstore middleware validates `subject` + `scope` + `prefix` against the requested operation BEFORE invoking `FsBlobStore`.

**Ownership model (compat with content-addressed dedup):**

Content-addressed storage means N uploaders can produce the same `sha256` — no natural "owner" on the blob itself. Solution: a separate `blob_grants` table in `index.sqlite`:

```sql
CREATE TABLE blob_grants (
    subject       TEXT NOT NULL,     -- "agent/<id>" or "user/<id>"
    store_key     TEXT NOT NULL,
    perms         TEXT NOT NULL,     -- "r" | "rw" | "rwd"
    created_at    INTEGER NOT NULL,
    PRIMARY KEY (subject, store_key)
);
```

- A new upload publishes a new grant row on the existing-or-new blob — no copy.
- Read check: middleware verifies a `(subject, store_key, perms ⊇ requested)` row exists.
- **Dedup invariant preserved:** bytes live once on disk; grants are the access-control plane.

**Non-goals (Phase 2):**
- mTLS / per-agent certs (complex cert mgmt; doesn't distinguish multiple agents on the same host).
- Per-blob ACL (vs prefix scoping): only if granular sharing requirements emerge — not anticipated.

**Implementation tracking:** no issue filed yet — this section is the design record. Filing trigger = first concrete Phase 2 trigger condition met (see above).

## Consequences

### Positive

- Drops a primitive (NATS Object Store) we would have outgrown within months.
- Native dedup via content-hash; same blob shared 5× = stored 1×.
- Training/debug data is queryable with `sqlite3` immediately and exportable to parquet/duckdb without a NATS client.
- NATS messages stay slim (only `BlobRef` payloads); 50 MB JetStream ceiling stops being a transport concern.
- Hub memory profile flattens — no more raw-byte spikes per audio exchange.
- Migration to MinIO/S3 is a backend swap, not a contract or call-site refactor.
- Eager-ingest pattern eliminates Telegram/Discord URL-race failure modes.

### Negative

- v1 is single-host. Cross-host transport (e.g., STT on M₁ + TTS on M₂) requires a backend swap before it can work.
- Single-disk failure = total blob loss for v1. Acceptable only because data is stated as re-collectable; this constraint is now load-bearing on the ADR and must be revisited if that assumption changes.
- Adapters must implement eager download + SHA-256 hashing on ingress — a small per-platform cost.
- Yet-another internal interface to maintain (`BlobStore`), although a deliberately small one.

### Neutral

- A new package home is required (`roxabi-blobs` or extension of `roxabi-nats`); decided in the spec.
- `BlobRef` adds two fields beyond minimum (`platform_message_id`, `created_at`); these enable training-data reconstruction and provenance — not strictly necessary for transport, but cheap to carry.
- Deprecation window for `audio_b64` / `audio_bytes` will live across at least one release cycle.
- **Volume separation from JetStream (`#1055`):** the blob mount (e.g., `/data/lyra/blobs` + sibling `index.sqlite`) must be a distinct filesystem from the JetStream `store_dir` mount provisioned by [#1055](https://github.com/Roxabi/lyra/issues/1055). The two growth domains must not share a filesystem — unbounded blob growth must not be able to impact NATS durability (KV stores, streams, message persistence). #1055 remains independently valuable for JetStream; the original "prereq for slice 7" dependency in #1061 dissolves with the NATS-OS drop.
