## Source

> "Aujourd'hui, on a corrigé plein de petits issues, mais à chaque fois qu'on a corrigé une petite issue, on se retrouvait dans la situation où ça a recréé plein d'autres petits issues."
>
> — Trigger of the deep-dive investigation, 2026-05-19 evening

This document captures the full root-cause analysis, architectural decisions, and rollout strategy from the investigation conversation 2026-05-19 → 2026-05-20. It is the **reference document** for Epic #1277 and all 7 phase issues (#1278-#1284). The Epic body is a condensed summary; this artifact is the exhaustive analytical record.

## 1. Context — observed pattern (2026-05-19)

Empirical signal from a single day's work:

| Metric | Value |
|---|---|
| PRs merged | ~14 |
| PRs still open at end of day | 7 |
| Branching factor (new issues / closed issue) | ≥1.5 |
| Sibling-fixes for a single bug class (`str(exc)` leak) | 5 (#1212 → #1215 → #1219 → #1252 → #1253 → #1256) |
| Small PRs opened in a 7-minute window | 7 |

Three distinct cascade shapes observed simultaneously:

- **Lineage cascade**: a bug class fixed in one site exposes the next site via /code-review → next fix → next site. Each fix is technically correct, but the class is never closed.
- **Review-deferral cascade**: each PR's /code-review generates ~7 "deferred warnings" → each becomes its own issue → each issue gets its own PR → each PR's review generates ~7 warnings.
- **Side-discovery cascade**: working in area A surfaces N latent issues in area B (test drift, stale paths, undocumented kwargs). Each filed as a separate issue.

The signal was **exponential**, not linear. Growth ≥1.5× per cycle = doubles every ~2 cycles.

## 2. Root cause analysis — 4 stacked producers

A 3-voice agent panel (architect / product-lead / devops) plus a code-quality audit (3 zones) plus a DEBT audit converged on a 4-producer model:

```
1. Boundary primitive↔intégration without typed abstraction  (architectural)
        ↓ produces latent duplications (8 dormant cascades identified)
2. When touched → /code-review surfaces sibling sites          (tooling calibration)
        ↓
3. Findings without Discard tier → all become filed issues    (process)
        ↓
4. Issues → DEBT-tagged → bucket "async-pipeline" w/o drain   (debt decoupling)
        ↓ tracking sans pressure de fermeture
        → la duplication latente persiste → 1. recommence avec plus de surface
```

Each layer alone is insufficient explanation. Together they form a self-stabilizing loop:

- Architecture (1) provides the latent duplications
- Tooling (2) detects them all when triggered
- Process (3) converts every finding into work
- Debt system (4) absorbs the work into untracked buckets, giving false closure

The 4th producer was the key insight: the DEBT registry is **technically irreprochable on filing** (98.6% noqa tag coverage, all exemptions linked to issues or ADRs) but **poisoned on draining** — all drain slices point to abstract buckets ("async-pipeline", "P2b") with no concrete GitHub milestones. `boundary-broad-catch` grew from ~85 → 104 sites in 19 days without any closed-loop drain pressure.

**Conclusion**: patching individual cascades treats symptoms. The root cause is structural — the system has no mechanism to make latent duplication impossible.

## 3. Altitudes of intervention

The investigation walked up an abstraction ladder:

| Altitude | Question | Mechanism | Coût | Bénéfice |
|---|---|---|---|---|
| Patch | Comment fixer ce bug ? | Edit 5 sites manually | jours | Tue 1 instance |
| Patch industrialisé | Comment empêcher ce bug ? | Typed port + import-linter + grep hook + test | semaine | Tue 1 classe |
| Logique | Comment garantir la correction ? | Invariants déclarés + tests universels | semaine+ | Tue toute classe déclarée |
| Architecture | Selon quel axe le système est-il découpé ? | Pivot d'axe de décomposition | semaines à mois | Tue la possibilité même de la classe |
| Plateforme | Le code intégration existe-t-il du tout ? | Runtime déclaratif | trimestres | Le concept disparaît |

Each higher altitude **renders lower altitudes less necessary** but doesn't replace all of them. A well-architected system still benefits from explicit invariants. An explicit-invariant codebase still benefits from well-calibrated tooling.

The chosen altitude for this refactor is **Architecture** — the highest tractable level given current bandwidth. Platform-level Lyra is noted as a future direction but out of current scope (trimestre+ effort).

## 4. The axis-of-decomposition insight

The file tree reveals Lyra's current axis:

```
adapters/telegram/   adapters/discord/   adapters/cli/
nats/nats_llm_client.py
nats/nats_tts_client.py
nats/nats_stt_client.py
nats/nats_image_client.py
llm/drivers/cli_nats.py    llm/drivers/claude.py
integrations/supervisor.py  integrations/vault.py
```

**One file = one integration target.** Each target accretes the same M concerns (parse, validate, sanitize, route, retry, log, timeout, circuit-breaker, metrics).

Growth function: **N targets × M concerns = N × M sites**. Multiplicative.

Consequences (mechanical, not anecdotal):

- Bug in a concern → N target files to fix → cascade
- New target → copy-paste M concerns from neighbor → drift
- New concern → add to all N targets → cascade
- Audit finds duplication → confirms what the axis predicts

**The cascade is not a pathology. It is the predicted consequence of the chosen axis.** Until the axis changes, no amount of patching closes the loop.

### The alternative axis: by stage / capability

Decomposition by horizontal slice of the data flow (stage) or by transverse concern (capability):

```
stages/{parse, sanitize, route, execute, emit}.py
capabilities/{retry, throttle, circuit_breaker, heartbeat}.py
```

A target becomes a **pipeline configuration**, not a code file:

```python
telegram = Pipeline(
    wire_in   = TelegramParser,
    sanitize  = DefaultSanitizer,
    transport = NatsRequestResponse,
    business  = HubDispatcher,
    wire_out  = TelegramEmitter,
    caps      = [Retry(3), Throttle(20), CircuitBreaker()],
)
```

Growth function: **N + M modules**. Additive.

Consequences:

- Bug in a concern → 1 module to fix → 0 cascade possible
- New target → compose existing stages → no drift
- New concern → 1 module, applied automatically via composition

### Why Lyra ended up with the target axis

Honest hypothesis (not a reproach):

- 1st adapter written → contains everything because common stages aren't yet identified
- 2nd adapter → cost-of-factoring > cost-of-copy-paste at that moment → copy is rational
- 3rd adapter → the axis is locked, factor-cost prohibitive

Lyra adopted **hexagonal architecture nominally** (`core/ports/`, hexagonal boundary tests) but in practice the "ports" are nominal Protocols without the stages being factored behind them. **Hexagonal in name, not in structure.**

The code-quality audit confirmed this empirically: SDK layer (`roxabi-nats`) — crisp, audit rating 4.5/5. Per-client satellite layer (`nats/nats_*_client.py`) — copy-paste-over-abstract, audit rating 3.5/5. Same project, two different architectural disciplines, both visible.

## 5. Target architecture — 3-layer composition

For the worker-pool family (NATS clients), the target architecture is:

```
┌─────────────────────────────────────────────────────────────┐
│ Domain clients (LlmClient, TtsClient, SttClient, ImageClient)│  ~80 lines each, thin
│   • encode / decode                                          │
│   • domain logic only                                        │
└─────────────────────┬───────────────────────────────────────┘
                      │ composes
┌─────────────────────▼───────────────────────────────────────┐
│ WorkerPoolClient (generic, parameterized)                    │  ~200 lines
│   • circuit breaker per-pool                                 │
│   • heartbeat lifecycle                                      │
│   • worker registry / freshness                              │
└─────────────────────┬───────────────────────────────────────┘
                      │ composes
┌─────────────────────▼───────────────────────────────────────┐
│ NatsTransport                                                │  ~150 lines
│   • call(pool_id, bytes) → Result[bytes, SanitizedError]     │
│   • never raises                                             │
│   • sanitize() internal                                      │
└─────────────────────────────────────────────────────────────┘
```

**Architectural commitments encoded in the structure**:

- **`Result[T, E]` return type** — callers cannot ignore errors (no exception path) and errors are pre-sanitized (no `str(exc)` path)
- **Composition over inheritance** — no class-attr override magic, no `__init_subclass__` validation hooks; dependencies visible in constructor signatures
- **Domain doesn't see transport details** — encode/decode operate on bytes, not on `nats.errors.Error` or connection metadata
- **Capabilities (CB, heartbeat, registry) live ONCE** in `WorkerPoolClient`, not duplicated per domain

Same pattern propagates to other zones (adapters in/out, LLM drivers, stream processors) — see Phase decomposition below.

## 7. Architectural decisions (U1-U5)

Resolved unknowns from the planning conversation, applicable principally to Phase 1 but propagating to subsequent phases.

### U1 — `Result[T, E]` type implementation

**Decision**: native Python tagged union (~25 lines).

```python
from dataclasses import dataclass
from typing import Generic, TypeVar

T = TypeVar("T"); E = TypeVar("E")

@dataclass(frozen=True)
class Ok(Generic[T]):  value: T

@dataclass(frozen=True)
class Err(Generic[E]): error: E

Result = Ok[T] | Err[E]
```

**Rationale**:
- Zero new dependencies
- pyright type-narrows correctly on `isinstance(r, Ok)`
- No friction "what's `bind`?" for new readers
- Consistent with project's "invariants, not inventory" style (CLAUDE.md)

**Rejected**: `returns` lib, `result` lib — too much monadic machinery for current needs.

### U2 — Composition over inheritance

**Decision**: full DI, abandon inheritance.

Before: `class NatsLlmClient(NatsWorkerClientBase)` with class-attr overrides.

After: `LlmClient(pool: WorkerPoolClient, codec: LlmCodec)` injected via constructor.

**Rationale**:
- Inheritance = the file-axis way of sharing code. The architectural pivot is precisely to STOP sharing by file.
- DI makes tests trivial (inject fakes)
- Dependencies become visible in constructor signatures (visible in pyright + IDE)
- `_worker_client_base.py` (created in #1235) will be deleted post-migration — its work isn't lost, it's replayed as composition

### U3 — Circuit breaker scope

**Decision**: per worker-pool, preserved.

The breaker semantically protects against worker failures (TTS workers crashing shouldn't break LLM). It is a **worker-pool concern**, not a transport concern.

→ Lives in `WorkerPoolClient`, not in `NatsTransport`. Transport stays pure plumbing.

### U4 — Heartbeat lifecycle

**Decision**: composed into `WorkerPoolClient`.

Was inherited via `NatsWorkerClientBase` (#1235 — the previous refactor iteration). The defense-in-depth + atomicity work done in #1235 is preserved, but moves from inheritance hook (`_on_heartbeat` override) to composition (constructor argument `heartbeat_subject`).

The class-attr validation hooks (`VALIDATE_WORKER_ID`, `__init_subclass__`) become constructor args. Simpler, no metaclass magic.

### U5 — Test restructuring

**Decision**: tests restructured by layer (transport / pool / domain), not rewritten from scratch.

- `tests/transport/test_nats_rr.py` — wire errors, timeout, no-responders
- `tests/transport/test_worker_pool_client.py` — circuit breaker, heartbeat lifecycle
- `tests/domain/test_llm_client.py` (and 3 similar) — codec + business, with fake `WorkerPoolClient`

The tautologies surfaced by tester agent during #1242 review (`test_any_alive_delegates_to_registry`, throttle_window dropped) disappear naturally during the restructure — they were tests of inheritance plumbing that no longer exists.

## 12. Future altitudes — beyond this epic

The investigation surfaced a higher altitude than chosen for this epic: **platform-level Lyra**.

> Au-dessus encore : passer de "Lyra est du Python qu'on commit" à "Lyra est un runtime qui interprète des intégrations déclarées".

Concretely: ajouter une cible = éditer 1 fichier YAML, pas commiter du Python. Le runtime applique les stages automatiquement.

**Cost**: refonte sur trimestres. **Benefit**: la classe entière de cascades disparaît du domaine — il n'y a plus de code d'intégration à corriger, parce qu'il n'y a plus de code d'intégration tout court.

This is noted explicitly here so that if the stage-axis refactor succeeds and the team gains confidence in declarative composition, the next altitude is identified and accessible. It is **not** committed work for this epic.

## Appendix A — How layers stack (worked example)

The `str(exc)` cascade case study illustrates how the 4 producers compose:

- **Layer 1 (architecture)**: `f"...{exc}"` pattern is constructible at any call site because no typed `SanitizedError` port exists. 5 sites latent.
- **Layer 2 (tooling)**: /code-review with 6 agents finds the 5 sites when one is touched. Each surfaced as a finding.
- **Layer 3 (process)**: each finding becomes "blocker" (fix now in this PR) or "deferred warning" (new issue filed). The 4 not in current PR scope → 4 new issues filed.
- **Layer 4 (debt)**: the `boundary-broad-catch` slug grows by ~15 sites in 19 days. Drain points to "async-pipeline" bucket. No closed-loop pressure.

Cycle complete. Next cycle starts when the next site is touched.

**After the refactor**:

- Layer 1: `port.emit(f"...{exc}")` does not type-check. The pattern is lexically impossible in non-transport code.
- Layer 2: /code-review cannot find sibling sites because there is one site (in transport).
- Layer 3: 0 deferred warnings generated for this class. Loop disengages.
- Layer 4: `boundary-broad-catch` stops growing for this concern category.

The loop doesn't slow down. It stops, mechanically.

## Appendix B — Methodology (how this analysis was conducted)

The investigation used multiple agent-based instruments in parallel:

- **3-voice panel** (architect / product-lead / devops) — each defended one hypothesis cluster, anticipated objections, found convergence/tension. Surfaced the layered-cause model.
- **3-zone code-quality audit** (core / adapters / nats-llm) — each sampled 5 files older than 3 days, evaluated clarity / abstraction discipline / error consistency / test quality / comment hygiene. Surfaced 8 dormant cascades.
- **DEBT inventory + recent-additions audit** — catalogued all `DEBT:` slugs, exemptions, noqa additions since 2026-05-01. Surfaced the drain-decoupling 4th producer.
- **Strategic impact map** — walked through ~75 open issues, categorized by conflict / synergy / orthogonality. Drove the absorb/close/pause decisions.

The total investigation took ~6 hours of conversation. The artifacts (this document, Epic #1277, Phases #1278-#1284, comments on absorbed/paused issues) capture the durable output.
