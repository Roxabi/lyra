## Problem

The hardcoded-constant gate (`tools/check_hardcoded_constants.sh`, #1654) shipped with a
grandfather baseline of **86 pre-existing numeric literals** in `src/factory/core/`
(`tools/hardcoded_constants_baseline.txt`). The baseline lets legacy magic numbers pass while
blocking *new* ones — a ratchet, not a fix. Until burned down, those 86 values remain scattered,
unnamed, and unconfigurable: timeouts, buffer sizes, retry counts, column counts and the like are
duplicated across files with no single source of truth.

This issue burns the baseline to zero: each entry is either (a) extracted to a named `Config` field
or `Protocol` constant, or (b) — for genuine false positives (docstrings like "24 columns",
row-length checks like `len(row) != 11`) — resolved with a justified `# const-ok:` marker or removed
from the baseline. End state: the baseline file has 0 active entries and the gate still exits 0 on a
clean tree.

## Who

- **Primary:** roxabi-factory maintainers — gain a single source of truth for core tunables and a
  gate that protects *all* constants, not just post-#1654 ones.
- **Secondary:** future contributors — clearer config surface; no more guessing whether a magic
  number is intentional or grandfathered debt.

## Constraints

- **No behavior change.** Pure refactor — every extracted constant must keep its current runtime value.
- **Axial review.** Changes are confined to `src/factory/core/` (intra-core); per CLAUDE.md the axial
  label triggers only when crossing the top-level `factory.*` module boundary — likely not triggered,
  but watch any `Config`/`Protocol` placement that pulls in `infrastructure`.
- **File-length + folder-size gates** (300 SLOC / 15 files) apply to any new/extended `*_config.py`.
- **Baseline regeneration is mechanical** (`--generate-baseline`) but must reflect real extractions,
  not laundering — see Out of Scope.
- Existing Config infrastructure to extend: `src/factory/core/config/{agent_defaults,bus,dispatch,
  lifecycle,memory,platform,turn_store}_config.py`.

## Out of Scope

- **No bulk `# const-ok:` laundering.** `# const-ok:` is reserved for true protocol/hard limits and
  documented false positives — not a mass escape hatch to empty the baseline cheaply.
- Constants outside `src/factory/core/` (the gate's `SCAN_ROOT`).
- Changing the gate script's detection logic or thresholds (2–6 digit window).
- Tuning the *values* of any constant — extraction only, values preserved verbatim.

## Premise Validity

**Success in 6 months:** `tools/hardcoded_constants_baseline.txt` has 0 active entries (file
deletable), and `check_hardcoded_constants.sh` exits 0 on a clean tree — every former magic number
now lives in a `Config` field, `Protocol` constant, or carries a justified `# const-ok:`.

**Failure in 6 months:** Baseline active-entry count stays > 0 after the work ships, OR the gate
regresses to exit ≠ 0 on a clean tree — magic numbers remain unextracted despite the burn-down PR
merging.

**Simplest alternative:** Bulk-delete the baseline file and `# const-ok:`-mark all 86 lines in place.
**Why not simplest:** That defeats #1654's intent — it launders the magic numbers as "approved"
without giving them names or a single source of truth; the constants stay scattered and
unconfigurable. Real extraction to Config/Protocol is the point.

## Complexity

**Tier: F-full** — high-volume (86 items × per-item judgment), spread across ~30 core files, requiring
false-positive triage and cross-file decisions on Config vs Protocol placement and naming.

Signals observed:
- 86 baseline entries across ~30 files in `src/factory/core/`
- Mixed nature: real tunables, protocol hard limits, and false positives (docstrings, row-length asserts)
- Requires categorization + placement strategy before a coherent spec — justifies the `analyze` step
- Single domain (core) but judgment-heavy, not mechanical
